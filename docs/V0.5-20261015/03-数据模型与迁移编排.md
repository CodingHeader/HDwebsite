# 03 数据模型基线与迁移编排

## 1. 现状

- 模型：46 张表（P04 恢复区块 4 表后；P06-verify 行数对比口径）。迁移 6 个：init → partner_int_id → course_sort → llm_kind_botid → `20261012134621_p04_data_integrity` → `20261012154723_p06_collect_kb_review`。回滚脚本：`prisma/rollback/p06.sql`。
- 约定：JSON-in-String、枚举为字符串、无软删除（审计靠 OperationLog）、高频过滤列有 @@index；P06 起“新增关联列不建外键”以避免 SQLite 整表重建（schema.prisma:605 注释）。

## 2. 唯一剩余迁移：`p12_knowledge_base`（W0-06，Wave 0 内完成，之后迁移全程冻结）

**为什么放到 Wave 0**：P12 原本是第 7 个迁移、排在 P11 之后。并行要求“不共用同一迁移版本号 ∧ 无共享可变状态”（规划总指令 §7.1）。把唯一的 schema 变更提前到冻结点，五条线在 Wave 1 都只读 schema，迁移串行链退化为一个节点。代价：C 线的业务代码要在已存在的表上开发（这正是契约先行的目的）。

**审查门槛**（W0-06 验收）：迁移 SQL 只含 `CREATE TABLE`、`ALTER TABLE … ADD COLUMN`、`CREATE [UNIQUE] INDEX`；出现 `DROP`、`RedefineTables`、`INSERT INTO "new_` 即退回改 schema（去掉 relation）。在 p06 状态库副本上 `migrate deploy` 后：既有表行数不变、`PRAGMA integrity_check`=ok、`foreign_key_check` 为空；`rollback/p12.sql` 执行后 schema 与 p06 逐对象全等，且可再次 deploy。

## 4. 数据生命周期

- 运行时文件（uploads、kb、backups、数据库）不入 git：D-10 执行 `git rm -r --cached uploads`（先导出、计数一致才执行），`.gitignore` 增加 `uploads/`、`data/`。
- 备份：`DATA_DIR/backups/`，含 db + uploads + kb，保留 14 份（D-10）。
- 删除级联由应用层完成（无外键）：删 KnowledgeBase → 删其 KnowledgeFile 与 Knowledge 条目 → 删磁盘文件 → 请求 Coze 删除（失败只记录）（C-06）；删 Media → 删 4 个文件（D-11）。
