## 二、并行判定

可并行 = 无共享可变状态 ∧ 契约已冻结 ∧ 文件所有权不重叠 ∧ 迁移号不冲突。

| 卡 | 改动文件 | 与谁重叠 | 判定 |
|---|---|---|---|
| FIX-01 | `src/app/manager/{articles,chat-history,collect-items,content-hub,home-blocks,knowledge-bases}/page.tsx` | 无 | **可并行** |
| FIX-02 | `src/components/manager/CrudPage.tsx`（`displayName`）+ `content-hub`/`publish-jobs` 两页的 toast description | ⚠️ 与 FIX-01 **重叠 `content-hub/page.tsx`** | **须串行或拆分** |
| FIX-03 | `src/lib/crud-resources/collect.ts` | 无 | **可并行** |

### 2.1 FIX-01 与 FIX-02 的重叠点

两卡都改 `src/app/manager/content-hub/page.tsx`：
- FIX-01 改 `emptyAction`（空态，约 `:356`）
- FIX-02 改 toast description（成功态，`:197`）

**裁决**：**合并为一次提交，由同一执行会话顺序完成**（先 FIX-01 再 FIX-02，各自独立 commit）。理由：同一文件两处不相邻改动，合并提交会破坏"一卡一提交"的证据链；串行执行则无冲突。

因此实际并行度为 **2**（FIX-01→FIX-02 串行链 ‖ FIX-03）。

## 三、为什么 FIX 组必须在 B2 之前

| 理由 | 说明 |
|---|---|
| ① 避免缺陷重复计入 | B2 验 172 格、B3 验 172 格。带着 11 个已知 FAIL 去验，会让这些缺陷在 B2/B3 的 matrix 里再次出现，污染 FAIL 统计 |
| ② 避免掩盖新问题 | 若 B2 报 30 个 FAIL，其中 11 个是旧的，独立验证者无法区分新老 |
| ③ 判据一致性 | FIX-01 修完空态后，B2 的 K1/K2 在空态页面上的键盘可测性才成立（空态无按钮 → Tab 无可聚焦元素） |

③ 是最强理由：**空态没有可聚焦元素时，K1（Tab 顺序）与 K2（主操作可聚焦）测不了**。FIX-01 补齐空态动作后，B2 才有意义。

## 七、熔断规则

| 情形 | 处置 |
|---|---|
| 同卡连续 2 次 FAIL | 停止，改写卡片或标 `blocked`，上报规划者 |
| 触碰冻结面（N-1~N-7） | 立即停止该子项，写 CCR |
| 发现新缺陷 | 记 `05-风险与待裁决.md`，**不自行扩范围** |
| 环境不可用（Lighthouse/Docker） | 记 UNKNOWN，不冒充 PASS |
