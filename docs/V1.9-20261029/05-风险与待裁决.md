# 05 · 风险与待裁决

## 一、BLOCKING（改代码前必须裁决）

### B-01 · `collect-tasks` 搜索字段能否用关联字段

| 项 | 内容 |
|---|---|
| **位置** | `src/lib/crud-resources/collect.ts:32` `searchFields: []` |
| **问题** | `collectTask` 无自有可搜文本字段（`source` 是关联 `collectSource.name`）。改为 `["source"]` 需确认 Prisma 查询构造器是否支持对关联字段做 `contains` |
| **方案 A** | `searchFields: ["source"]`，若能生成 `source: { name: { contains } }` |
| **方案 B** | 保持 `[]`，前端隐藏该页搜索框（`searchFields` 空即"不可搜"语义） |
| **方案 C** | 改判据为 N-A —— **不采纳**：搜索框仍在页面上，用户输入无效无反馈 |
| **共同部分** | 都承认"搜索框存在但无效"是缺陷 |
| **分叉点** | A 需泛化过滤器（可能触 `src/lib/crud-*.ts` 通用逻辑），B 只需前端条件渲染 |
| **谁裁决** | 规划者（技术实现选择，非产品方向） |
| **当前决议** | 先由执行者做技术验证；A 不成立则走 B，不触发 CCR |

### B-02 · `banners` / `enrollment-offerings` 无可用实体名

| 项 | 内容 |
|---|---|
| **位置** | `src/components/manager/resource-meta/specs.ts` banners（`image/link/sort/status`）、enrollment-offerings（`majorId/partnerId/sourceBatch/...`） |
| **问题** | 两者都没有 `displayName()` 候选键里的字段，toast 无法点名 |
| **方案 A** | 扩 `displayName()` 候选键（如加 `image`、`sourceBatch`） |
| **方案 B** | 在两页的 spec 里标 `primary` 列，用该列作为名称 |
| **方案 C** | 各页 `toast.success` 显式传描述（绕过 `displayName`） |
| **共同部分** | 都要求"toast 须点名所建实体" |
| **分叉点** | A 改共用组件（影响 27 页），B 改两页 spec，C 改两页调用 |
| **谁裁决** | 规划者 |
| **当前决议** | **优先 C**（最小影响面，不动共用 `displayName`）。若 C 无法拿到名称（新建时响应体不含可读字段），退 B |

## 五、规划纪律改进项（供后续轮次采纳）

V1.8 的三张卡（B1/B2/B3）**同时把页数写成 42**，实测 43。根因相同：**卡片基数取自估算，未与代码对账**。

V1.9 的纠正手段：**所有基数类断言必须附可执行命令**，例如：

```bash
find src/app/manager -name page.tsx | wc -l    # 43
```

建议写入后续规划纪律：

> 凡卡片中出现"N 页 / N 格"的基数，必须同时给出产生该数字的命令，且该命令可直接复跑。无命令的基数视为假设，不得作为验收依据。
