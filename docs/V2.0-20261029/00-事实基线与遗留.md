## 三、遗留 1 · E2E 2 FAIL

### 现象

```
e2e: 77 PASS / 2 FAIL
位置：tests/e2e/hub-content.spec.ts:22 与 :53
```

### 原文

```ts
// tests/e2e/hub-content.spec.ts:22（创建流程）
await page.getByRole("button", { name: "创建" }).click();
await expect(page.getByText("草稿已入库")).toBeVisible();     // ← 断言旧文案

// :53（审核拒绝流程）
await page.getByRole("button", { name: "创建" }).click();
await expect(page.getByText("草稿已入库")).toBeVisible();     // ← 同一断言
```

### 成因

FIX-02 改了 content-hub 的创建 toast（`src/app/manager/content-hub/page.tsx:196`）：

```ts
// 改前
toast.success("已创建", "草稿已入库，可提交审核。");
// 改后
toast.success("已创建", `「${body.title}」已入库，可提交审核。`);
```

**旧子串「草稿已入库」被替换为「「<标题>」已入库」**，断言失配。

### 定性

**真缺陷**（跨卡断链）。FIX-02 改文案时未同步 e2e 断言，E1 又禁改 `tests/**`，故遗留。

### 危险信号

`:22` 与 `:53` 都用 `getByText("草稿已入库")`。若改成 `getByText("已入库")`，两处都能过 —— 但这是**放宽断言**（`已入库` 是更短的子串，可匹配更多内容）。

**必须改为与新文案语义等价的断言**，见 `E2E-01` 卡。

## 四、遗留 2 · B3 的 40 个 M3 FAIL

### 统计

### 关键发现：40 个 FAIL 只有一种尺寸

```bash
$ node -e "...按 observed.primaryW×primaryH 分组..."
尺寸分布: { '76x36': 40 }
总 FAIL: 40
页面: 40 个不同页面
```

**40 页、40 格，全部是 `76×36`。**这不是 40 个缺陷，是**一个按钮令牌**在 40 页上的重复显现。

`76×36` 对应 `Button` 默认 `md` 尺寸：

```ts
// src/components/manager/ui/button-class.ts:24
const sizes = {
  sm: "h-8 px-2.5 text-[12px] ...",     // 32px
  md: "h-9 px-3.5 text-[13px] ...",     // 36px  ← 命中区 36px
  lg: "h-10 px-4 text-[14px] ...",      // 40px
};
```

### defects.md 记录的其它控件

```text
新建 按钮：76×36（高 36px <44）
搜索输入框：343×36（高 36px <44）
content-hub 新建内容：68×32
notify-rules 编辑：70×32
collect-items 审阅：52×32
login 输入框：293×40 / 登录按钮：293×40
```

### M2 零 FAIL 的意义

```
M2 核心操作可达：36 PASS / 0 FAIL / 7 N-A
```

**所有核心操作都能到达且生效。** M3 是纯尺寸问题，不影响功能可用性。这决定了 M3-01 的优先级与风险等级 —— 它是体验改进，不是功能缺陷。

## 五、遗留 3 · D1-FIX PARTIAL（LCP）

### 三种测量的巨大差异

| 口径 | LCP | CLS | 说明 |
|---|---|---:|---|
| Lighthouse 模拟（Slow 4G + 375） | **3.1~3.3s** | 0.208→0 | 未达 good（≤2.5s） |
| 无节流 | 见 after.md | 0 | — |
| **真实浏览器（PerformanceObserver）** | **136ms** | **0** | 优秀 |

来源：`docs/design/06_validation/evidence/V19/D1-FIX/after.md:38-40`

### 模拟口径的不确定性

```
after 两轮 LCP 元素漂移：footer 段落 ↔ logo <img>
@13 复测 LCP 元素回到 logo <img>
```

**LCP 元素在两轮之间漂移** —— 元素不稳定，说明该指标在模拟环境下不具确定性。

### 定性

**不是缺陷**。真实值 136ms 远优于 2.5s 阈值。CLS 真实值 0，已完全达标（模拟口径的 0.208 也已被改进到 0 —— 归因是 `<footer class="bg-[#da251d]">` 的单一 layout-shift）。

**需裁决的是判据口径**，不是代码。

### 冻结面冲突（实证）

`className` 值被**实质改写**，不只新增属性：

```diff
-<div className="fixed right-4 bottom-20 z-50 flex flex-col gap-3">
+<div className="fixed right-3 bottom-16 md:right-4 md:bottom-20 z-50 flex flex-col items-end md:items-stretch gap-2.5 md:gap-3">

+          className="w-11 h-11 md:w-10 md:h-10 rounded-full bg-white/20 flex items-center justify-center group-hover:scale-110 transition-transform"
```

对比 REQ-F-014：**「组件 JSX/className 与 main 逐字一致；允许差异仅限 import 路径、类型、数据适配层、XSS 净化、Markdown 渲染、SEO/埋点」**。移动端响应式类不在允许差异清单内。

### 但这是用户授权的

按用户 2026-10-29 裁决（移动端导航问题），该改动被授权。**问题不在改动本身，在于没有留 ADR** —— 导致：

1. 下次独立验证者看到 `className` 与 main 不一致，会判 FAIL
2. 无法区分「授权的例外」与「违规改动」
3. 也无法说明为什么允许破例（用户看到的实际问题是遮挡/竖排）

### 附带：`prisma/seed.ts` 改动

`prisma/seed.ts` 不在 `src/contracts/**` 也不在迁移目录，**不属于冻结面**（AGENTS.md §4 冻结的是 `prisma/schema.prisma` 与迁移）。但它是数据种子，改动影响数据基线，需在 ADR 中记录理由（院校 13 家）。

```bash
$ git log -1 --format=%h%x20%ad --date=short -- tests/visual/reference/

$ git log -1 --format=%h%x20%ad --date=short 88e72d69
```
