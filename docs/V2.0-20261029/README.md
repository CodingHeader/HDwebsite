## 五、两个待裁决（详见 `05-风险与待裁决.md`）

### D-20-01 · 44px 判据是否成立、按什么范围实施

**这是本轮最重要的一条。** 44px 的出处经查证是：

| 出处 | 原文 | 约束对象 |
|---|---|---|
| V1.3 `STEP-S3.md:27` | 「375px 下命中区 `min-h-11`（≥44px）」 | **审核单选项** |
| V1.4 `06-验收体系.md:73` | Q6「375px 核心操作可完成 \| 375 e2e + 命中区 ≥44px」 | 宽泛表述 |
| V1.8 B3 卡 `README.md:57` | M3「命中区 ≥44px \| ≥44×44」 | **全部核心控件** |

**判据从「审核单选项」扩张到了「全部核心控件」**。扩张本身有依据（44px 是移动端触控通行标准），但它带来一个真实的设计冲突：管理端按钮令牌是 `h-9`（36px）紧凑密度，提升到 44px 会让整个管理端在 375px 下显著变松。

**我的建议（方案 B）**：**仅在 375px 视口内**提升到 44px，用响应式类实现（`h-11 md:h-9`），**桌面端保持 36px 不变**。这样既满足移动端触控，又不动桌面密度。

### D-20-02 · LCP 判据用哪个口径

模拟（Slow 4G）3.1~3.3s vs 真实浏览器 **136ms**，差 24 倍。且模拟下 **LCP 元素在两轮间漂移**（logo `<img>` ↔ footer `<p>`）—— 元素不稳定说明指标本身在该环境下不具确定性。

**我的建议**：判据以真实浏览器 `PerformanceObserver` 为准（136ms 优秀），模拟值仅作趋势记录，**不作为 PASS/FAIL 门槛**。同时**不做代码优化**（真实值已优；若真需优化，目标在 footer，属前台冻结面）。

## 六、基线事实

### B3 的 40 个 FAIL 是 1 个根因

```bash
$ node -e "...读取 cells.json..."
FAIL 按项: { M3: 40 }
尺寸分布: { '76x36': 40 }     ← 40 页全是同一个尺寸
页面: 40 个不同页面
```

`76×36` 即 CrudPage 页头 `新建` 按钮（`Button` 默认 `md` → `h-9` = 36px）。

其余三项判据：

| 项 | PASS | FAIL | N-A |
|---|---:|---:|---:|
| M1 无横向溢出 | 41 | 0 | 2 |
| M2 核心操作可达 | 36 | **0** | 7 |
| M3 命中区 ≥44px | 1 | **40** | 2 |
| M4 卡片模式 | 38 | 0 | 5 |

**M2 零 FAIL**：所有核心操作都能到达且生效。M3 是纯尺寸问题，不影响可用性。

### 视觉基线已 stale

```bash
$ git log -1 --format=%h -- tests/visual/reference/
ad4cf70e                      ← 2026-10-27
$ git log -1 --format=%h --date=short 88e72d69
```
