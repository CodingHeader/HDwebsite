## 二、每卡取卡循环（严格按序）

```text
1. 拉代码   git fetch origin upgrade && git pull --ff-only
           核对 git rev-list --left-right --count origin/upgrade...HEAD == 0 0
2. 读状态   cat docs/V1.5-20261027/state.json
           取 status=ready 且 depends_on 全部 done 的卡
3. 领卡     改 status 为 in_progress
4. 读卡     docs/V1.5-20261027/tasks/<卡号>.md
5. 构建前置 ★ 若卡内要求跑构建/e2e：先 npm run build，并确认 BUILD_ID 新于 src
             （tests/e2e/global-setup.ts 已硬校验，stale 会直接抛错）
6. 执行     只在「允许修改」路径内写入，越界即 FAIL
7. 门禁     只跑本卡「验证命令」列的（阶段体检，不跑全量）
8. 证据     docs/design/06_validation/evidence/V15/<卡号>/execution.md
            必含：5W1H、改动文件、验收逐条结果（含判据）、命令输出摘要、UNKNOWN
9. 提交     git commit -m "feat(V15-XXX): ..."（小而聚焦）
10. 推送    git push origin upgrade；被拒只 rebase，禁 force
11. 心跳    state.json 改 done + commits + note
12. 回到 1
```

## 三、四条铁律（均有实测教训）

### 1. 阶段体检，不跑全量（本轮用户指令）

```text
单卡只跑它改到的测试。
全量（lint && typecheck && test && build + e2e）只在 V15-CLOSE-01 跑一次。
```

**依据**：`06 §1.2` 三条 + 一条自我否定防守。**这不是偷懒**：7 卡中 6 卡不碰 `src/**`。

**防守**：每卡验收含 `git diff --name-only` 只含允许路径的硬断言。越界即 FAIL，不依赖测试发现。

### 2. e2e 证据必须附 BUILD_ID 时间戳（V13 教训）

```text
BUILD_ID mtime = <ISO>
src 最新 mtime = <ISO>
关系 = fresh / stale（stale 则结论作废）
```

`tests/e2e/global-setup.ts` 已硬校验。

### 3. 验收必须写"判据"而非只写结论（V1.4 教训 H4）

```text
❌ | articles | PASS |
✅ | articles | PASS | 空态：筛选"不存在关键词" → 显示"没有匹配结果"+新建按钮；加载态：Slow 3G → 3 行骨架 |
```

无判据的 PASS 视为 FAIL。

### 4. 禁止改 `src/**`（本轮全部 7 卡）

V1.5 是验收轮。改代码会让"验收对象"变化，形成自证。若发现必须改代码才能过 → 标 `blocked` 并开新卡，不在本卡内改。

## 四、并行纪律（写进规划，让执行者看到）

```text
✅ 允许并行：不同 evidence 目录、同一冻结契约、0 迁移
❌ 禁止并行：

```

## 五、阻塞与升级

| 情形 | 动作 |
|---|---|
| 发现 `src/**` 必须改才能通过 | 标 `blocked`，开新卡，**不在本卡内改** |
| 审计脚本修正后仍有争议 | 升级 `opus`，由 main-agent 裁定 |
| 人工验收发现某页确实缺态 | 记录 FAIL + 现象，**不修**（本轮不改代码），转 V1.6 |
| B1~B5 裁决被推翻 | 停 S2，重写判据后重跑 |
| 连续 2 次验收失败 | 熔断：重写任务卡 / 升档 / 标 blocked，**不撞第 3 次** |
