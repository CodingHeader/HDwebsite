# 01 · 需求基线复核

> 纪律：不默认现有需求文档完整、准确、无歧义。以下为独立复核结论。

## 1.1 复述与拆解

### 一句话复述

弘道教育需要一个**官网 + 管理后台一体化**系统：管理端统一管理内容（文章/课程/图集/专业/合作伙伴等），内容经采集或人工录入后进入审核，审核通过后**同时分发到官网与微信公众号**两个渠道；官网呈现给访客（含 AI 客服、在线报名），管理端提供给运营/编辑/管理员三类角色使用。

### 拆解与关键词

| 维度 | 关键词 | 代码载体（证据） |
|---|---|---|
| 内容源 | 采集、人工录入、Markdown | `src/lib/collect-engine.ts`、`src/app/manager/content-hub/` |
| 审核 | 待审/通过/拒绝/编辑后入库 | `src/app/manager/`（content-hub 审核链路） |
| 分发 | 官网 + 公众号 双渠道 | `src/lib/publish-executor.ts`、`ContentChannel` 模型 |
| 官网呈现 | 16 页、Banner 轮播、红色横幅风格 | `src/app/(web)/**/page.tsx`（16） |
| 管理端 | 42 页、CRUD、五态、`mgr-*` 令牌 | `src/app/manager/**/page.tsx`（42） |
| AI | 多模型优先级 + 兜底、知识库 | `src/lib/llm-gateway.ts`、`src/app/manager/knowledge-bases/` |
| 通知 | SMTP 邮件、事件驱动 | `src/lib/notify-*`、`src/app/manager/notify-rules/` |
| 身份 | 三角色、JWT、会话签发 | `src/contracts/auth.ts` |

### 用户 / 管理端 / 边界

- **终端用户**：访客（无需登录）—— 浏览官网、看课程、在线报名、AI 客服问答
- **管理端用户**：ADMIN（全权）/ EDITOR（内容编辑）/ VIEWER（只读）—— 证据：`src/contracts/auth.ts` 角色枚举
- **系统边界**：
  - 内：自有 SQLite + Next.js 单体 + 本地文件存储（`DATA_DIR`）
  - 外：微信公众号 API、SMTP、Coze 知识库、LLM 供应商
  - 明确**不做**：多租户、Redis/MQ/独立 worker（`AGENTS.md §5` REQ-C-003）

| # | 未知项 | 为什么 BLOCKING | 条件方案 A | 条件方案 B | 共同部分 | 分叉点 | 需裁决的变量 |

| B1 | 42 页键盘可达的**判定标准**是什么？ | 标准不同会导致"全部通过"或"全部返工"两种相反结论 | 按最小集：Tab 顺序合理 + Esc 关闭弹窗 + 主操作可聚焦 | 按完整集：再加 ⌘/Ctrl+S 提交、焦点陷阱、skip-link | 都需实测 42 页 | 是否需要焦点陷阱与快捷键 | 「达标」的口径 |

**默认方案（A）及其依据**：`tasks/V14-UI-CONSIST-01.md:30` 原文写"焦点陷阱、Esc 关闭、⌘/Ctrl+S 提交"三项。但实测 `CrudPage` 未实现焦点陷阱（`grep -c "focus-trap\|FocusTrap"` = 0）。若按完整集判，会得到"42 页全 FAIL" —— 那等于要求重做整个管理端，超出 V1.5 范围。
**故默认按 A（最小集）**，并把「焦点陷阱是否必需」列为待裁决（07 §B1），不擅自扩大范围。
