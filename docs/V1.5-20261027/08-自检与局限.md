## 三、本次规划的局限（自我否定）

### L1 · "第一刀是步行骨架"不完全适用

**问题**：指令 §5.3 要求第一刀必须是"能跑通的最小闭环（健康检查 + 鉴权写接口 + 一张表 + 一次迁移 + 前端打到真实 API + 统一错误响应）"。

**现实**：V1.4 已完成该骨架，且 102 条验收已判定 90 条。本轮若强行做一个"新骨架"，属无需求支撑的伪造任务。

**处置**：第一刀改为"解锁依赖最多的前置"（台账归位）。**这是对指令的偏离，已显式登记，不隐瞒。**

### L2 · S0 / S3 低于"2 小时独立成刀"门槛

**问题**：指令 §5.2 要求"小于 2 小时的改动不要单独成刀"。

**现实**：S0（台账回填，约 5 分钟）与 S3（收口，约 30 分钟）均低于门槛。但 S0 必须在最前（解锁）、S3 必须在最后（收口），物理上无法并入相邻刀。

**处置**：保留独立，按 `haiku` 计，不占 `opus` 券。

### L3 · Setting 键数统计口径不一致，未查明

**现象**：`V1.4/06-验收体系.md` 写"Setting 键 **85**"；本轮实测 `grep -oE '^\s+[a-zA-Z][a-zA-Z0-9]*:' src/lib/settings-registry.ts | wc -l` → **约 35**。

**可能原因**（未验证，故不下结论）：
- V1.4 的 85 可能统计的是"注册表中所有 key 字符串"（含嵌套/别名）
- 本轮正则只抓顶层标识符，可能漏掉 `def("a.b.c", ...)` 形式的点分 key

**处置**：本轮**不把该数作为验收依据**（`03 §三` 已声明 `03 §四` 不依赖它）。若要精确统计，需解析 registry 的实际 `def()` 调用参数 —— 列为后续待办，不在 V1.5。

### L4 · Dialog 的 Esc 处理结论基于 grep，未经运行时验证

**现象**：`grep -nE "Escape|onKeyDown|key===" src/components/manager/ui/dialog.tsx` **无命中**（文件 98 行）。

**局限**：可能 Esc 处理在 `FormDialog.tsx` 或 `CrudPage.tsx` 的父级 `onKeyDown` 上，grep 只查了 dialog.tsx。

**处置**：`07 §二 U5` 已登记为未决假设；由 `V15-KEYBOARD-01` 的 K3 实测确认。**不得仅凭 grep 就判定"Dialog 无 Esc"并写进最终验收报告。**

### L5 · 观察者偏差：本规划由 main-agent 编写，且后续 S2 也由 main-agent 执行

**风险**：可能出现"自己定标准、自己判通过"的自证循环。

**缓解**：
- 验收标准（`06 §四`）在本规划阶段写定，**执行时不得修改**
- S2 的判定对象是外部助手写的代码（V1.4 的 `src/**`），main-agent 是独立方
- S3 收口由外部助手执行，交叉核对证据完整性
- 每格必须写"判据"（做了什么、看到什么），可被第三方复现

**残余风险**：仍在同一会话内完成，无法完全排除先验偏见。**已登记，不宣称"绝对客观"。**

### L6 · 未验证 CI 证据的完整性

**现象**：本轮引用 V1.4 的 CI 结论（run `40471824511`、`40472734510` 全 success）来自上一轮实测记录，**未在 V1.5 重新验证**。

**依据**：`AGENTS.md §6` Done 定义要求证据可复现。上一轮已留 `evidence/V14/VIS-STAB-01/stability.md`，本轮采信该证据，不重复拉取。

**局限**：若 CI 状态在两次会话之间发生变化（如仓库被回滚），本规划的"基线绿"前提不成立。**收口时（S3）需重新确认 HEAD 与 CI 状态。**
