## 四、可并行组（机械判定）

判定规则（四条全满足才算可并行）：

```text
① 无共享可变状态
② 依赖的契约已冻结且机器可校验
③ 文件所有权不相交
④ 不共用同一迁移版本号（本轮 0 迁移，恒满足）
```

## 五、关键路径

```text
A1(0.3h) → A2(0.7h) → A3(3h) → A4(1.5h) → A5(1.5h) → A8(2h) = 9h
                                                                  ↓
                                                            E1(1h)
```

**关键路径总长 10 小时**（A 组串行链 + E1）。

对比：
- B 组（15~19h）可与 A 组并行 → 不占关键路径
- C/D 组可与 A 组并行 → 不占关键路径

**所以理论最短工期 = max(关键路径 10h, B 组 19h) = 19 小时**（若 B 组并行执行）。


## 八、阶段顺序的自我质疑

**质疑 1：为什么 B 组（验收）排在 A 组之后？**
→ 因为 B 组要用 `audit-matrix.md` 作判据基础，而该矩阵的 PageHeader/令牌两项由 A2/A8 修正。若 B 先做，会基于错误矩阵得出错误结论。

**质疑 2：C2（API 缓存）为什么不是最高优先级？**
→ 因为它是**性能优化**非能力对等。且原版也无 HTTP 缓存（`grep Cache-Control` 原版 0 处），不属退化。低优先级合理。

**质疑 3：D1（Lighthouse）值得单列一阶段吗？**
→ 值得，因为它是 REQ-NF-001 唯一未判定的条目（UNKNOWN）。但它需 CCR 装依赖，实际可能 blocked。单列能让它独立受阻而不拖累其他阶段。

**质疑 4：E1 是否必要？**
→ 必要。`state.json` 的 16 个阶段状态、changelog V1.8 段、双端一致性都需要一个收口动作。且它是唯一跑全量门禁的阶段。
