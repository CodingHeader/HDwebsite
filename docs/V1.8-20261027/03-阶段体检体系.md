# 03 · 阶段体检体系

> 用户要求：**每张卡只跑它改到的测试，每个阶段结束做一次体检，全量回归只在最后跑一次，不设门禁。**
> 本文把这个要求落成一张可执行的表。

---

## 一、总体原则

```text
单阶段：只跑本阶段改到的检查（秒级~分钟级）
阶段末：一次体检（本阶段动过的模块）
全量：只在 E1-V18收口 跑一次
门禁：不新增，不改 ci.yml 必需项
```

### 为什么不按阶段跑全量

**① 代码位置**：16 阶段中 **13 个不碰 `src/**`**（B1~B3 只写 evidence、D 组只读测量、E1 只改台账）

**② 实测**
```bash
# 各阶段是否触及 src/**
A1 → contracts/setting.ts        （碰）
A2 → lib/settings-registry.ts    （碰）
A3 → components/web/*.tsx        （碰）
A4 → app/(web)/*.tsx             （碰）
A6 → manager/ai-config/page.tsx  （新增）
A7 → lib/image-exists.ts         （新增）
C1 → lib/showcase-guard.ts       （新增）
C2 → lib/api-handler.ts          （碰）
其余 8 个 → 只写 docs/evidence  （不碰）
```

**③ 推断**：对不碰代码的 8 个阶段跑 `npm test`/`build`，边际收益为零，且 `test:e2e` 单轮约 3 分钟 × 8 = 24 分钟纯等待。

## 三、唯一的全量门禁（E1）

```bash
# 必须串行（V1.3 教训 H2：并行 build+test → Hook timed out in 10000ms）
npm run lint && npm run typecheck && npm test && npm run build
npm run check:assets && npm run check:root && npm run check:audit
node scripts/check-frozen.mjs
```

**② 凭据**：`AGENTS.md §7` 列出验证命令；V1.3 实测并行产假红（`07-自检与局限.md §H2`）

**③ 落点**：`E1-V18收口/steps/STEP-E1-2.md`

### 条件性补充

| 门禁 | 何时加跑 | 依据 |
|---|---|---|
| `npm run test:visual` | A5 已跑过一次；E1 若 `git status src` 非空则重跑 | A5 是视觉变更点 |
| `npm run test:e2e` | 仅当 C2 改了 API 响应头可能影响 e2e 断言时 | C2 触及 `api-handler.ts` |

### win32 限制（影响 E1 能否全绿）

**① 代码位置**：`next.config.ts:7`
```ts
output: isWindows ? undefined : "standalone"
```

**② 实测**
```bash
grep -n "isWindows" next.config.ts → :3 定义, :7 使用
# 基线图在 Linux 生成（45 张）
ls tests/visual/reference | wc -l → 45
```

**③ 处置**：
- `test:visual` 本机必失败（字体差异）→ 记 `UNKNOWN(需 Linux CI)`
- `test:e2e` 本机不可跑 → 记 `UNKNOWN(需 Linux CI)`
- **不得声称通过**
- CI push 后自动跑，以 CI 结论为准

## 四、每阶段体检的产出格式

每个阶段目录的 `steps/` 末尾有 `STEP-*-Z-体检.md`，要求记录：

```markdown
## 阶段 <X> 体检

| 项 | 命令 | 结果 | 判据 |
|---|---|---|---|
| <检查1> | `<cmd>` | exit 0 / PASS | <为什么这个结果说明通过> |
| <检查2> | `<cmd>` | ... | ... |

### 未跑项及原因
- <项>：<为什么不跑 / 何时跑>

### UNKNOWN
- <项>：<原因 + 何时能消>
```

**关键**：每项要写**判据**，不只写结果。反例：`| tsc | PASS |`（无判据）。

## 五、完成定义（每阶段）

```text
阶段 Done =
  所有权内 diff 符合 README 的任务定义
  ∧ 验收条目逐条 PASS/FAIL/UNKNOWN
  ∧ 本阶段体检表全项有结果
  ∧ 未越界（git status 只含允许路径）
  ∧ evidence 可复现
  ∧ 未改冻结面（className 值 / 基线图 / 阈值 / schema）
```

## 六、体检与「不设门禁」的关系

用户要求「不设门禁」。本文的处理：

| 项 | 是否门禁 |
|---|---|
| 各阶段体检 | **不是门禁** —— 只记录，不阻断 |
| E1 全量 | **不是门禁** —— 跑一次记录结果 |
| CI 现有门禁 | **不动** —— 保持原样，不加不减 |

**区别**：门禁是「不过就拦」，体检是「跑了记录下来」。本轮全部是后者。

**唯一的硬约束**：`git status` 越界 → 阶段 FAIL。这不是门禁，是所有权纪律。

## 七、自我质疑

**质疑：不设门禁会不会让缺陷流入？**
→ 可能。缓解：每阶段体检表强制写结果 + E1 跑全量 + CI 现有门禁仍在（push 后自动跑）。三重记录，只是不「阻断式」拦截。

**质疑：B 组三卡要 15~19h 人工验收，期间不跑任何测试合理吗？**
→ 合理。B 组的产出是 `evidence/V18/B*/matrix.md`（纯文档），不产生代码，跑测试验证不了任何东西。

**质疑：C2 改 `api-handler.ts` 影响 52 个路由，只跑 `tsc` 加 `curl -I` 够吗？**
→ **不够**。这是我这张表里唯一站不住的一处。C2 的体检必须加 `npm test`（单测覆盖 api-handler）+ 抽样 5 个路由 `curl -I`。已在 C2 阶段 README 中修正。
