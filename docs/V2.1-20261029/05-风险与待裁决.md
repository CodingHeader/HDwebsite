# 05 · 风险与待裁决

## 一、BLOCKING（须用户裁决，不得假设）

### B-1 · 推送与拉取的凭据

**现象**：

```bash
$ git fetch origin
fatal: could not read Username for 'https://github.com': No such file or directory
```

**已排除的误判**：
- 不是网络问题：`git config http.proxy = http://127.0.0.1:10808` 已配置，且代理实测可用（此前 `curl -x http://127.0.0.1:10808 https://github.com` 返回 200）
- 不是仓库地址问题：`remote.origin.url = https://github.com/nevermeetagain/HDwebsite.git` 与用户提供的一致

**根因**：HTTPS 方式需要凭据，本机无凭据存储/助手。

**三个方案**：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A** | 用户提供 PAT，经临时环境变量 + 内联 credential helper 使用，用后即清 | 不改 remote | 需用户提供凭据 |
| **B** | 改用 SSH：`git@github.com:nevermeetagain/HDwebsite.git` | 一次配置长期有效 | 需该仓库的 SSH key 授权 |
| **C** | 本地提交完成，推送延后 | 不阻塞开发 | 双端不一致，违背用户要求 |

**共同部分**：本地 commit 可先完成，不阻塞规划与执行。
**分叉点**：是否现在就具备推送条件。
**建议**：方案 A 或 B，**由用户选择**。本轮不擅自改 remote。

**已有证据（不足以定论）**：

- 因此若用户开的是 3000，现象可完整解释；若开的是 6789，则现象无法用现有代码解释 → 需截图
