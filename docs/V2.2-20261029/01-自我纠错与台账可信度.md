# 01 · 自我纠错与台账可信度

> 规则：优先自我否定。本节列出我上一轮判断中的错误，以及我对 `parity-matrix.md` 台账的独立复核结果。

---

## 一、我的错误 E-1：基线差异归因不完整

### 1.1 我上轮说了什么

`docs/V2.1-20261029/05-风险与待裁决.md` B-4 节，以及 V2.1 CHANGELOG 中，我写：

> 「只有 `88e72d69` 有影响」

### 1.2 实测是什么

```bash
$ git log --oneline ad4cf70e..5f92871 --no-merges -- "src/app/(web)/" "src/components/web/" | cat
88e72d69 fix(web): 手机端导航竖排 + 悬浮层遮挡 + 导航对齐 main + 院校 13 家
69acba52 fix(V18/A5): Banner 第二按钮接线位置修正 —— 移入 bannerSettings
646b5135 fix(V18/A4): 还原 FloatingContact 二维码容器的 overflow-hidden
296f7a8e feat(V18/A4): 首页接线 —— 11 键透传 + 二维码 + 遮罩
6851b015 feat(V18/A3): 9 组件 props 恢复 —— showOverlay/showContent/bgImage/extraBtn
221d2bc5 feat(V18/A7+C1): 前台数据层复用与守卫 —— localImageExists 提取 + showcase 过滤
49aaf043 feat(V14-A11Y-01): a11y 门禁接入 CI + 前台 5 页 axe（消灭孤儿测试）

$ ... | wc -l
7
```

**7 个提交**，不是 1 个。

### 1.3 错误的性质与后果

| 维度 | 判定 |
|---|---|
| 性质 | **归因不完整**（看了单个提交就下结论，没做区间 `git log`） |
| 是否数据造假 | 否。`88e72d69` 确实是主因，我没有编造数字 |
| 后果 | **会误导操作**：若按我的说法只关注 375 图，会漏掉 `home-1440`/`home-768`（由 V18/A3-A5 引起） |
| 执行者是否正确 | **是**。他做了区间 `git log` 并逐张比对，13 张（`home` 三视口 + 10 个 `-375`）与 7 个提交吻合 |

### 1.4 我为什么犯错（反思路径）

我当时只执行了：

```bash
git merge-base --is-ancestor ad4cf70e 88e72d69   # 得到"基线早于该提交"
git diff 91ea5bb..HEAD -- 'src/components/web/**' --stat
```

前者只证明时间先后，后者只看**区间总 diff**，没有**按提交拆分**。两者都不能得出"只有 1 个提交有影响"的结论——我把"时间上最近的关键提交"当成了"唯一有影响的提交"。

**正确做法应是**：`git log <基线>..<HEAD> -- <路径>` 列出全部触碰提交，再逐个判断是否有视觉影响。

### 1.5 这类错误如何防

写入后续规划纪律：

> 凡断言「只有 X 有影响」，必须先运行区间 `git log <from>..<to> -- <path>` 列出**全部**候选提交，并说明其余提交为何被排除。不得以单个提交的时序关系替代全量枚举。

## 二、我的错误 E-2：抽验方法不可靠

### 2.1 我做了什么

为验证 parity 台账可信，我用文件名推断路径：

```bash
$ ls src/lib/notify/smtp.ts
MISS
```

我一度准备把它记为「台账声明与代码不符」。

### 2.2 实际是什么

```bash
$ grep -rln "nodemailer\|createTransport" src/lib/
src/lib/notify-gateway.ts
src/lib/__tests__/lane-b/notify.test.ts
src/lib/__tests__/notify-before-publish.test.ts
```

SMTP 逻辑**内联在 `notify-gateway.ts`**，台账 F11 说的正是「notify-gateway：…」，**从未声明存在 `smtp.ts`**。

### 2.3 结论

**这是我的抽验方法错，不是台账错。** 凭「我以为它应该叫这个名字」去构造路径，属于**用猜测补全关键事实**（违反硬约束 §1.2）。

**已修正的方法**：`PAR-01` 卡强制要求用 `git ls-files` / `grep -rl` 反查，不得路径猜测。

## 三、parity 台账的独立复核

### 3.1 台账的自我声明

`parity-matrix.md` 第 22-28 行：

| 状态 | 数量 | 说明 |
|---|---:|---|
| present | 50 | A1~A22 + B1~B17 + C1~C11 + D1~D4 + E1~E3，共 57 行中 50 项 |
| replaced | 7 | B4、B9、B10、C2、C3、D2、D3（经 ADR 替代，功能覆盖） |
| partial | **0** | 无 |
| missing | **0** | 无（旧版 11 条已关闭） |
| UNKNOWN | 1 | 真实微信/SMTP/Coze 联调（凭证缺失） |

F 节 11 项新增需求：**present 11 / partial 0**。

### 3.2 我的抽验（8 项路径存在性）

| 路径 | 结果 |
|---|---|
| `src/lib/wechat.ts` | OK |
| `src/lib/llm-gateway.ts` | OK |
| `src/lib/notify-gateway.ts` | OK |
| `src/lib/collect-engine.ts` | OK |
| `src/components/web/ChatWidget.tsx` | OK |
| `src/app/api/chat/stream/route.ts` | OK |
| `src/lib/kb/coze.ts` | OK |
| `src/lib/jobs/backup.ts` | OK |

**8/8 存在**。

### 3.3 抽验的局限（诚实标注）

- 只覆盖 8 个路径，台账有 57 行主表 + 11 行 F 节
- 只验证「文件存在」，**未验证「行为正确」**
- 未验证 7 个 `replaced` 项的 ADR 是否真的覆盖了原功能

**分级：台账声明 = 部分确认，不是已确认。** PAR-01 的职责就是把「部分确认」推到「已确认」。

### 3.4 台账的可信度评价（辩证）

**支持台账可信的证据**：

1. 台账**主动记录了自身的局限性**（第 30 行：「旧计数是 P01 期快照…矩阵正文一直未重算。本次逐行复核后重算」）
2. 台账**披露了历史缺口的关闭对照**（11 条 missing + 21 条 partial 逐一列出关闭原因与提交）
3. 台账**改进了判据口径**（2026-10-21 起把「视觉风格不一致」从 partial 中剥离，交给独立门禁）——这是**提高标准**，不是降低
4. 抽样 8 项全部命中

**反对台账可信的证据**：

1. 8/57 的抽样率过低，不足以支撑「missing=0」的全称断言
2. 台账曾长期未重算（自认），说明存在「写完就不维护」的历史
3. `present` 判据是「功能与行为在 upgrade 可用」——「行为可用」需要运行时验证，而台账多数条目只有静态路径引用
4. `replaced` 7 项依赖 ADR 覆盖性，ADR 是否真的等价覆盖原功能，台账未逐项论证

**综合判断**：台账作为**索引入口**可信（它诚实地标注了历史与口径），作为**验收结论**不足（缺运行时验证）。这正是 PAR-01 存在的理由。

## 五、对后续规划的约束（自我约束条款）

1. 任何「只有 X」的全称否定断言，必须附区间枚举命令与输出
2. 任何路径存在性判断，必须用 `git ls-files` 或 `grep -rl` 反查，不得凭命名推断
3. 任何跨模块影响判断，必须先确认两模块是否真的相关（如 visual 是否覆盖 manager）
4. 「我无权限」只说明我这条路不通，不等于「无法验证」；须说明是否存在其它可行路径
