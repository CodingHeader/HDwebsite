# 02 · 未实现需求核查

> 本轮需求的字面要求是「检查未被实现的需求」。本节把「未实现」拆成三类分别判定，避免用一句话概括掉真实差异。

---

## 一、三种「未实现」，必须分开

用户说「需求没实现」，可能指三件完全不同的事。混在一起会导致修错方向。

| 类型 | 含义 | 判定方法 |
|---|---|---|
| **T1 功能缺失** | 需求要求的功能在代码里根本没有 | parity 台账 + 代码存在性 + 运行时可用性 |
| **T2 可运行性缺失** | 功能写了，但照文档跑不起来 | 按 `.env.example` 配置后能否启动 |
| **T3 可追溯性缺失** | 有实现，但无据可查（无 ADR/无记录），无法判断是否合规 | 差异 vs 记录 |

---

## 二、T1 功能缺失：判定为 0（部分确认）

### 2.1 台账声明

`docs/design/02_requirements/parity-matrix.md` 第 22-28 行：

```
present  50
replaced  7
partial   0
missing   0
UNKNOWN   1   （真实微信/SMTP/Coze 联调，凭证缺失）
```

F 节 11 项新增需求：present 11 / partial 0。

### 2.2 我的独立抽验

| 层级 | 证据 |
|---|---|
| E1 需求 | REQ-F-001 ~ REQ-F-015（`docs/design/02_requirements/features/`，15 个文件实测存在） |
| E2 实现 | 8 个代表性路径全部存在（见 `01-自我纠错与台账可信度.md` §3.2） |
| E3 验证 | 只做存在性验证，未做运行时验证 |

**结论：missing = 0 属「部分确认」**，不是「已确认」。

### 2.3 为什么不给「已确认」

- 抽样率 8/57 ≈ 14%，样本不足
- 「present」的判据是「功能与行为可用」，「行为可用」需运行时验证，台账多为静态路径引用
- 7 个 `replaced` 依赖 ADR 覆盖性，台账未逐项论证等价

**推算理由（非结论）**：如果 8/8 抽样都命中且台账主动披露了历史缺口与口径变更，缺 43 项里全都有问题的概率不高。但「概率不高」不是「已确认」，PAR-01 就是为此存在。

### 2.4 一项真实的功能边界（不是缺失，是环境限制）

| 项 | 状态 | 说明 |
|---|---|---|
| 微信公众号 API 真实联调 | UNKNOWN | 凭证缺失，按 AGENTS.md §2 口径 |
| SMTP 真实联调 | UNKNOWN | 同上 |
| Coze dataset 真实联调 | UNKNOWN | 同上 |
| `docker build` | UNKNOWN | 本机无 docker CLI |

**这四项不是「没实现」**——代码存在、mock 测试覆盖，只是无法验证真实连通性。归入 UNKNOWN 而非 missing，是正确的口径。

## 三、T2 可运行性缺失：判定为「存在真缺陷」

这是本轮最有价值的发现。

### 3.1 缺陷 1：`.env.example` 与 `env.ts` 自相矛盾

**E1 来源**：AGENTS.md §7「本地需 `.env.local`（JWT_SECRET ≥32 位等，参照 `.env.example`）」

**E2 实现**：

```bash
# .env.example 第 5-10 行（原文，逐字）
# 字段加密密钥（AES-256-GCM，覆盖 LLM apiKey/微信 appSecret/SMTP password；默认派生自 JWT_SECRET）
# ENCRYPTION_KEY=

# 数据库（默认 file:./prisma/dev.db）
# DATABASE_URL="file:./prisma/dev.db"

# 站点域名（邮件/素材绝对链接使用）
# APP_DOMAIN
# APP_ORIGIN=https://www.hd1994.com
```

```ts
// src/lib/env.ts:38-56（原文）
const isProd = env.NODE_ENV === "production";

// JWT_SECRET / ENCRYPTION_KEY：任何环境都要求
for (const key of ["JWT_SECRET", "ENCRYPTION_KEY"] as const) {
  const v = env[key];
  if (!v) { issues.push(key); }
  else if (v.length < 32) { issues.push(`${key}(长度<32)`); }
}

// 仅生产要求其余键
if (!isProd) return issues;

for (const [key, test] of Object.entries(PROD_REQUIRED)) {
  if (key === "JWT_SECRET" || key === "ENCRYPTION_KEY") continue;
  const v = env[key];
```

其中：

```ts
// src/lib/env.ts:16-21
const PROD_REQUIRED = {
  JWT_SECRET:    (v) => v.length >= 32,
  ENCRYPTION_KEY:(v) => v.length >= 32,
  DATABASE_URL:  (v) => v.startsWith("file:") || v.startsWith("http") || v.startsWith("libsql:"),
  APP_ORIGIN:    (v) => /^https?:\/\//.test(v),
} as const;
```

**E3 验证**：V2.1 期间实测生产启动：

```
[env] FATAL: 以下环境变量缺失或不符合要求，拒绝生产启动（只列键名，不显示值）：
  - ENCRYPTION_KEY
  - APP_ORIGIN
```

**矛盾逐条**：

| # | `.env.example` | `env.ts` 实际 | 后果 |
|---|---|---|---|
| 1 | `ENCRYPTION_KEY` **注释掉** = 暗示可选 | 任何环境缺失即 FATAL | dev 也起不来 |
| 2 | 「默认派生自 JWT_SECRET」 | **全仓库无派生代码**，直接读 `env.ENCRYPTION_KEY` | 照文档做必失败 |
| 3 | `DATABASE_URL` 注释掉 | 生产 `PROD_REQUIRED` 必须 | 生产启动失败 |
| 4 | `APP_ORIGIN` 注释掉 | 生产必须 | 生产启动失败 |

**当前实证**：`.env.local` 只有 `JWT_SECRET` 一个键：

```bash
$ sed 's/=.*/=<hidden>/' .env.local
JWT_SECRET=<hidden>
```

→ **按现有配置 + 现有 `.env.example`，生产启动必然失败**。这不是理论推演，是 V2.1 已复现过的现场。

### 3.2 缺陷 2：`dev.db` 为 0 字节

```bash
$ wc -c prisma/dev.db
0 prisma/dev.db
```

**E3 验证**（V2.1 实测启动日志）：

```
[scheduler] 扫描异常： PrismaClientKnownRequestError
Invalid `prisma.cronJob.updateMany()` invocation:
Database error. Code: `1`. Message: `SQLITE_ERROR: no such table: main.CronJob`
```

**影响链**：

```
dev.db 0 字节
  → 无表
    → 前台 200 但所有数据区块回落硬编码默认值（`自考`×17 是默认文案，非 DB 数据）
    → 后台列表/统计因缺表 500
    → 调度器每分钟失败一次
```

**用户可感后果**：打开首页看到的是「默认演示态」而不是真实数据，容易误判为「设计变了」（这正是 B-2 待裁决的那件事的可能成因之一）。

### 3.3 缺陷 3：无环境自证手段

```bash
$ grep -c hdwebsite src/app/api/health/route.ts
0
```

`/api/health` 存在（`src/app/api/health/route.ts`），但不含应用标识。任何人无法用一条 curl 确认「我打开的是 HDwebsite 还是 Aidean」。

**这直接导致本轮最初的问题**：`:3000` 是 Aidean、`:6789` 是 HDwebsite，用户打开 3000 看到 Aidean 的界面，误以为 HDwebsite 被改坏了。

## 四、T3 可追溯性缺失：判定为「部分」

### 4.1 前台 className 差异的三档定性（沿用 V2.1 AUD 契约）

| 组件 | main 独有值 | HEAD 独有值 | 定性 |
|---|---:|---:|---|
| StatsBanner | 0 | 0 | ✅ 完全一致 |
| TopBanner | 0 | 1 | ✅ 合规（新增包裹层） |
| Banner | 0 | 2 | ✅ 合规（新增 extraBtn 类） |
| Navbar | 1 | 2 | ⚠️ **有据**（V10-Q1，用户 2026-10-24 授权，源码注释可查） |
| FourCards | 2 | 2 | ❌ **无据改写** |

### 4.2 FourCards 的无据改写

```diff
-    <section className="bg-gray-50 py-6">
+    <section className="bg-gray-50 py-6" style={sectionStyle}>
-        <div className="grid grid-cols-1 sm:grid-cols-2 md:grid-cols-3 gap-4 max-w-5xl mx-auto">
+        <div className={`grid grid-cols-1 sm:grid-cols-2 md:grid-cols-3 gap-4 max-w-5xl ${gridAlignClass}`}>
-                    <div className="relative flex-shrink-0 w-14 h-14 rounded-full bg-white/20 …">
+                      <div className="relative flex-shrink-0 w-14 h-14 rounded-full bg-white/20 …">
```

**关键差异**（值集合层面）：

```
main 独有：className="relative flex-1"
HEAD 独有：className="absolute inset-0 bg-black/40 group-hover:bg-black/30 transition-colors"
          className="absolute inset-0 bg-cover bg-center transition-transform duration-300 group-hover:scale-105"
```

`relative flex-1`（flex 布局的图标容器）被替换为 `absolute inset-0 …`（绝对定位覆盖层）——**这是结构性改写，不是新增能力**。

**为什么判「无据」**：
- `docs/design/03_solution/decisions/` 下无对应 ADR
- V1.8 A3 卡记录的是「恢复 props（showOverlay/showContent/bgImage）」，未提「改为绝对定位背景层」
- ADR-039 追认的是 `88e72d69` 的 `FloatingContact.tsx`/`Navbar.tsx`/`data/home.ts`，**不含 FourCards**

**但注意辩证**：`absolute inset-0 bg-cover` 可能正是 `bgImage` 能力（V1.8 A3/A4 恢复的配置键）的实现方式。若如此，它是**有需求来源的**，只是没写 ADR。这正是 AUD-02 要判定的：**合规 / 缺陷 / 待裁决**。

### 4.3 视觉基线差异的可追溯性（已被执行者解决）

`79df243` 的 13 张变化，执行者已逐张给出归因（`home` 三视口 ← `data/home.ts` 内容；10 个 `-375` ← `88e72d69` 移动导航）。**这一项的可追溯性已恢复。**

## 五、核查结论

| 类型 | 结论 | 依据强度 |
|---|---|---|
| **T1 功能缺失** | **0 项**（部分确认，抽样 8/57） | 中 |
| **T2 可运行性缺失** | **3 项真缺陷**：`.env.example` 矛盾 / `dev.db` 0 字节 / 无应用标识 | **强**（逐行代码 + 实测日志） |
| **T3 可追溯性缺失** | **1 项待判**：FourCards 无据改写 | 中（需 AUD-02 定性） |

### 5.1 对用户原话的回应

> 「检查未被实现的需求」

**直接回答**：功能性需求**没有发现缺失**；但**可运行性需求有 3 处未实现**。如果用户感受到的「需求没实现」是指「按文档跑不起来」或「打开的界面不对」，那这三项就是答案。

### 5.2 一个必须说的限定

我**没有**逐条验证 57 行 parity 主表的运行时行为（只抽验了 8 个路径的存在性）。所以「功能缺失 0 项」是**基于台账 + 抽样**的判断，不是全量实测。若用户要求「逐条验证」，需要 PAR-01 卡完整执行，预估 6~8 小时。

## 六、本轮核查的方法局限

| # | 局限 | 影响 |
|---|---|---|
| L-1 | 抽验率 8/57 | 「missing=0」证据不足 |
| L-2 | 未跑任何测试 | 行为正确性未验证 |
| L-3 | 未启动服务做端到端验证 | 可运行性结论基于代码+trace 日志，非现场重启验证 |
| L-4 | `:3000`/`:6789` 归属依赖进程命令行 | 若用户用的是别的宿主/端口，结论需重算 |
| L-5 | FourCards 的「无据」只基于「找不到 ADR」，不代表「一定无授权」 | 可能存在于聊天记录或口头裁决 |

**L-5 特别说明**：我判定「无据」的证据是「仓库内找不到记录」，这是**可核查的否定**（`ls docs/design/03_solution/decisions/` + `git log -S`），不是「我认为没有」。
