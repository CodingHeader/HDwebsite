# 01 需求基线复核（以 2026-10-13 的真实代码为准）

## 1. 复述与拆解

**核心问题**：弘道教育官网在**不改变访客所见风格**（main 的红色横幅轮播）的前提下，把旧站全部功能迁入 upgrade，并把官网与公众号的内容生产（自动采集 → 知识库 → 审核 → 自动发布 → 邮件提醒）与 AI 客服（多模型优先级 + 知识库 + 提示词 + 参数）统一到一个顶级易用的管理后台。P0~P06 已完成骨架与业务闭环；**剩余工作集中在：管理端体验（组件/页面/富文本/a11y）、知识库 Coze 集成与场景绑定、接口统一与响应契约、运维（启动/配置/缓存/存储/资源守卫）**。

- 访客：浏览、报名、AI 咨询（官网浮窗/报名页/公众号）。不新增访客能力，**前台只允许数据层/缓存/兜底字面量改动，视觉门禁 46/46 为硬约束**。
- 管理端：SuperAdmin（唯一审核权）/Editor/Viewer。
- 系统边界：单机 Next.js 16 + SQLite + 本地文件；外部 = 微信公众平台、SMTP、LLM（OpenAI 兼容/Coze）、被采集站点。无 Redis/MQ/独立 worker（REQ-C-003）。

## 5. 隐含要求与前置条件

- 隐含：五条线互不通信 → 唯一共享物是 tag `w1-base` 上冻结的契约、迁移、依赖与本规划；任何线需要改冻结面都必须走《契约变更请求》（11-验收与审查规程 §4）。
- 隐含：每条线的独立验证者不能是该线执行者（防自证循环）。
- 前置：W0 全部 8 张卡 PASS；D8 裁决；执行者机器能 `npm ci` 与安装 Playwright 依赖。
- 歧义：“知识库模型管理”按 P01 口径 = 知识库实体管理（Coze dataset 映射），嵌入模型属 COULD。
- 边界：SQLite 并发写（busy_timeout 已 5000ms）、公众号 5s 被动回复、SSE 断流、Coze 每批 ≤10 文件、知识库单文件 ≤10MB、上传 ≤20MB、采集图片 ≤10MB（D-12 统一常量）。
- 模块依赖：采集 → kb-sync → 知识库 → chat-service → 渠道；发布执行器 → 渠道注册表 → 写失效（cache-tags）→ 前台缓存。
