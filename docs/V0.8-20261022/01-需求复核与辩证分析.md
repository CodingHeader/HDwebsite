# 01 需求复核与辩证分析

## 1. 复述
HDwebsite 是一个教育机构官网（前台 web）加内容管理后台（/manager），后台包括内容中枢、发布、采集、知识库和 AI 场景。本项目要在 `upgrade` 分支上重构 main：**main 已有的功能，upgrade 必须都有**（备注 2）；main 没有的功能，在 upgrade 上扩展。前台保持 main 的红色横幅风格（D1），后台追求顶级易用（D5）。
用户分两类：访客（前台，匿名）和管理员（角色加权限，超管唯一可改 isSuper）。系统边界：微信公众号、SMTP、Coze、LLM 提供商都是外部系统，凭证尚未提供（D4）。

## 3. 5W1H（只写本轮新增的判断）

- **What**：功能面已基本闭环；剩下的是「安全依赖 + 验证面（visual/e2e/Linux）+ 体验收尾」。
- **Why**：V0.7 的「Done」大多在 Windows 上取证。visual 和 Docker 必须在 Linux 上才有效，这是**环境问题，不是代码问题**。如果不先补齐 seed 数据和 CI，任何样式修复都无法验证。
- **Where/When**：K10 必须最先处理（RCE）。visual 修复必须排在 seed 和 CI 之后。lint 清零排在所有改 src 的卡之后，否则会反复冲突。
- **Who**：Hark 负责 next 升级、前台视觉修复、后台 UX 状态收尾、终审（核心或高难度，以 UI 为主）；P1/P2/P3 负责中等和简单卡。
- **How**：每张卡都有可复制执行的验证命令；独立验证者只看命令输出。
- **What if**：Q1 不授权 → SEC-01/02/03 和下游 PERF/UI/T-03 标 blocked，其余 11 张卡照常推进（见 06 的 B 方案并行组）。CI 不可用 → VIS 卡标 UNKNOWN，绝不以 Windows 结果冒充。端口：按原配置，next start 默认 3000，env.ts 中 productionPort 已集中校验（69c814c）。

## 4. 钢人论证：V0.7「38/38 关闭」是否可信？

- **支持**：每张卡都有提交和独立复审文件（例如 826d39a、e57fa1f、bf0eeb2）；本轮复跑 lint/typecheck/test/build 结果见 00 §3；B-02/B-03 声称的 withApi 迁移，实测为 119 条路由中 114 条经 withApi 或 crud 工厂（crud.ts:119 内部包了 withApi）。
- **反对**：① e2e 中仍有 3 条 skip 写着「待 C-06/B-06 复跑」，而这两张卡已关闭，说明复跑没有真正执行。② visual 的 PASS/UNKNOWN 只有 Windows 证据。③ 「npm test 1705」是对方 Agent 的报告，需要以本轮实测为准。④ 有 5 条路由未经 withApi，没有找到豁免记录。
- **结论**：功能层面「部分确认」，验证层面「存在缺陷」。V0.8 不重做功能，只补验证与安全。
