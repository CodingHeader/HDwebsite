# 01 需求复核与辩证分析（V1.1）

## 1. 5W1H（本轮总体）

- **What**：约 50 条审计缺口 → 36 张卡，覆盖安全/公众号发布闭环/内容中枢 UI/采集调度/知识库 Coze/LLM 客服/邮件/管理端体验/招生/兼容 SEO/运维性能/终审。
- **Why**：V1.0 完成了"功能对等 + 门禁全绿"，但审计显示多处**上线功能不可用或语义错误**（公众号强制 freepublishEnabled 使草稿模式不可达、KB 上传从不推 Coze、检索页恒报失败、SMTP 阻塞主流程、XSS 放行畸形标签）——对等是"有端点"，深化是"真能用"。
- **Where/When**：upgrade 单主线；36 卡按 DAG 串并行混合；真实凭证类维持 UNKNOWN。
- **Who**：主代理（Hark lane：核心+UI）+ 两条子代理 lane（P1：采集/邮件/运维/招生后端；P2：限流/上传/LLM/兼容/SEO/e2e）；每切片子代理独立验证。
- **How**：每卡"现状盘点→修复→测试→证据"；切片收口跑全量门禁；state.json 台账。
- **What if**：审计文字与真实代码不符 → 以代码为准（卡内第一步即现状盘点）；修复引发回归 → 全量门禁拦截，按熔断处理；上游（微信/Coze）行为与文档不符 → 以实测为准并登记 UNKNOWN。

## 2. K1~K4 收敛拷问（苏格拉底式）

**K1（前台招生表）**：凭什么不加？——REQ-F-014 冻结是有约束力的用户裁决；上轮 Navbar 豁免是"明示个案授权"，本轮指令"不要问我"不构成对冻结的新豁免授权；加表改视觉可逆性差。反方：用户审计原文把"前台招生费用表在 main 里不存在"列为冲突，暗示想要。再反驳：同段也写了"与 REQ-F-014 冲突"——冲突的解法是裁决而非默认扩权。**默认：不加，登记可逆选项。**

**K2（上传规格）**：凭什么保持 20MB？——审计缺陷是"没有魔数校验"（安全性），容量是规格（产品决策）；收紧会破坏既有媒体工作流（回归风险），且规格变更从来需要用户点头。反方：设计文档写 ≤5MB。再反驳：设计文档早于实现演化，20MB 是既有现实；安全目标（拒伪装文件）由魔数达成，与容量正交。**默认：20MB 不动 + 魔数。**

**K3（推送）**：本机直推已被 V0.9/V1.0 十几次推送验证；沙箱失败仅因沙箱无凭据绑定。**直推。**

**K4（OG）**：meta 标签在 head，不进视口渲染，visual 基线（视口截图）不受影响；SEO 纯增益。反方：layout.tsx 属 (web) 冻结面？——metadata 增量不触碰 JSX/className（冻结按字面是"组件 JSX/className"），且 SEO 是 AGENTS 明列的允许差异（"SEO/埋点"）。**加。**

## 3. 关键修复方案的钢人论证（每切片最高风险项）

**SEC-01 XSS**：修复方向 = 畸形标签整体拒绝/强制闭合后再过滤，而非逐个正则补丁（正则法对 `</img onerror=...>` 类变体必有漏网——审计正是这么漏的）。白名单解析器（node-html-parser 或自研状态机）是强方案；风险是合法内容误杀——用既有净化单测 + 三详情页真实样本回归兜底。

**WX-03 发布模式**：把"能力开关"（freepublishEnabled 有没有）与"意图选择"（用户要草稿箱还是发布）解耦——判定矩阵入证据。风险：改判定可能破坏既有已配置任务 → mock 测试覆盖三种配置组合。

**HUB-02 externalId（CCR-1）**：契约唯一源最小增量（字段 optional），存量数据不受影响。反方：能不能不动契约？——渠道状态机要幂等去重必须有稳定外部标识，绕开契约会在组件里重复定义 DTO，违反更根本的纪律。用户指令已预批。**执行，最小增量。**

**ENR-01 唯一键空值**：SQLite 唯一索引把 NULL 视为互异 → 同键重复行。不动表（冻结）的前提下应用层 upsert 键归一化（空值→哨兵值比较）是唯一路径；若后续发现必须部分索引 → 停卡走迁移申请。
