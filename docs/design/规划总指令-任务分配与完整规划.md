# 任务分配与完整规划指令

你现在的任务：为当前项目产出**完整的任务分配与执行规划**。

---

## 0. 先理解你的产出会被如何使用

这决定了质量标准，请先读完再动手。

```
你的输出会被拆成 N 份独立的任务书
        ↓
分别交给 N 个**互相不能实时通信**的开发 CLI，并行执行
        ↓
它们唯一能共享的东西，就是你产出的「契约」
        ↓
结论：
  契约不完备      → 并行开发必然失败，融合阶段变成灾难
  任务卡不完整    → 执行者只能自己猜 = 违反纪律 = 返工
  所有权重叠      → 两个 CLI 改同一个文件 = 冲突覆盖
  依赖标错        → 阻塞或循环等待
```

所以你产出的不是"一份好看的文档"，而是**一组机器可执行的指令**。判断标准只有一条：

> **拿到你的输出，一个只具备局部上下文的执行者，能否在不追问、不猜测的前提下把活干完？**

---

## 1. 硬约束（不可协商）

```text
1. 默认只读。不得修改任何业务代码。仅可写入「规划产物」（见 §11 落盘清单）。
2. 禁止根据猜测补全关键事实。缺信息 → 标记 BLOCKING，不得编造。
3. 不得为凑数伪造方案或伪造任务。宁可少，不可假。
4. 所有结论必须能反向追溯到需求或真实代码证据。
5. 不得输出"绝对正确""一定成功"等无证据结论。
6. 不得用专家角色名望、行业惯例、"最佳实践"来提升方案权重——一切都必须落到本项目当前的证据上。
7. 遇到需求冲突或信息缺失，必须显式列出，不得静默替用户决定。
```

## 2. 第一步：建立事实基线（禁止跳过）

在提出任何规划之前，先完成事实采集。

### 2.1 读取项目规则

```text
[ ] 读取根目录 AGENTS.md（若存在）——其中的依赖方向、所有权、
    禁止行为、完成定义，是本规划的硬边界，你的输出不得与之冲突
[ ] 读取项目 README.md
[ ] 读取 docs/ 下的治理类文档（project-map.md / document-index.md / glossary.md）
```

### 2.2 检索并读取需求文档

需求文档可能位于项目内任意位置。请自行检索并全量读取，不要只读文件名的前几个。

必须覆盖：功能需求、非功能需求、约束需求、原始需求（inbox）。

### 2.3 核查真实代码状态

```text
[ ] 实际目录结构（不是文档里写的目录结构）
[ ] 实际技术栈与依赖（package.json / pyproject.toml / lockfile）
[ ] 实际已实现的模块与接口
[ ] 实际测试与测试命令（Makefile / package.json scripts / CI 配置）
[ ] Git 状态与最近提交
```

**关键纪律**：文档不是当前实现。文档说要做的，代码里可能没做；代码里有的，文档可能没写。两者不一致时，**以真实代码为准，并显式记录差异**。

### 2.4 建立规划快照

你的规划必须钉在一个确定的状态上，否则无法复现。

```yaml
snapshot:
  规划日期: <绝对日期>
  git_branch: <分支>
  git_commit: <commit hash>
  工作区是否干净: <true/false>
  需求文档清单: <路径 + 最后修改时间>
  代码文件数: <number>
  测试命令: <实际可执行的命令>
```

### 2.5 输出「事实基线」

```text
- 已确认的事实（有证据）
- 仅来自文档、未在代码中验证的（标注来源）
- 文档与代码不一致之处（逐条列出）
- 读取失败或无法访问的部分（不得跳过，必须说明）
```

## 3. 第二步：需求基线复核

需求虽然已由人理清，但**你仍必须独立复核**，不能默认它完整、准确、无歧义。

### 3.1 复述与拆解

```text
- 用一段话复述项目要解决的核心问题
- 分要点拆解需求，提取关键词
- 明确：谁是用户、管理端是谁、系统边界在哪
```

### 3.2 分级

把每条需求归入：

```text
MUST     必须有，缺失则项目不成立
SHOULD   应该有，缺失则体验受损
COULD    可以有，资源允许时做
MUST NOT 明确不做（这一项同等重要，它框定范围）
```

每条 MUST 必须能改写成**一句可验证的话**。改写不了 → 它还不是需求，是愿望 → 标记为待澄清。

### 3.3 冲突检查

```text
[ ] MUST 之间是否互相矛盾？
[ ] MUST 与 MUST NOT 是否冲突？
[ ] 非功能需求（性能 / 成本 / 工期）与功能复杂度是否兼容？
[ ] 需求与技术约束（端口 / 部署环境 / 已有技术栈）是否冲突？
```

### 3.4 未知登记册

列出所有未知项，逐条判定：

```text
BLOCKING      缺少它会导致规划发生根本性分叉 → 必须由人裁决
NON_BLOCKING  可先记假设 + 依据，继续推进 → 在任务卡中显式标注该假设
```

**纪律**：
- BLOCKING 项不得擅自假设。
- 但 BLOCKING 也不得导致整个规划停摆——必须输出：条件方案 A / 条件方案 B / 共同部分 / 分叉点 / 需人裁决的变量。

### 3.5 需求内部没有的、但执行必需的

主动识别并列出：

```text
- 隐含要求（用户没说但显而易见必需的）
- 未说明但必需的前置条件
- 可能产生歧义的表述
- 可能造成失败的边界条件
- 与其他模块的依赖
```

## 4. 第三步：契约冻结 ★

> **这是整个规划中最重要的产出。它是后续所有并行开发的唯一中间语言。**

在你的规划里，前端 / 数据 / 后端不是三个独立产品，它们共享同一张契约。**没有契约的并行，等于让三个互不通信的工人分别建地基、立柱子、砌屋顶。**

### 4.1 必须冻结的六份契约（少一份不准并行）

| # | 契约 | 必须包含 |
|---|---|---|
| ① | **API** | 路径、方法、请求 Schema、响应 Schema、分页格式、幂等语义、鉴权要求 |
| ② | **Errors** | 错误码枚举、HTTP 状态映射、错误体结构、前端如何展示 |
| ③ | **Identity** | 用户 ID 形态、角色枚举、session/JWT 声明、**管理端与用户端的权限边界** |
| ④ | **Resources** | 文件/图片 URL 规则、上传鉴权、访问控制、生命周期 |
| ⑤ | **Events** | 若有异步：事件名、载荷结构、触发时机、幂等键 |
| ⑥ | **UX States** | 核心界面的：空态 / 加载态 / 错误态 / 无权限态 / 成功态 |

### 4.2 契约的形式要求

```text
- 指定【唯一源】：从 OpenAPI / JSON Schema / zod / typia / 语言原生类型 中选一个
  其余一切从它生成。禁止多源并存。
- 契约必须是机器可校验的，不是自然语言描述
- 契约测试必须可从契约自动生成
- 字段命名、时间格式、金额单位、枚举取值，全项目统一
- 术语表：同一概念全项目只能有一个名字（写入 glossary）
```

### 4.3 数据模型基线

```text
- 核心实体与关系
- 每个字段：名称、类型、可空性、默认值、约束
- 索引策略（哪些查询路径需要索引）
- 迁移策略与版本号编排（★ 后续并行开发时迁移必须串行，此处定好顺序）
- 软删除策略与数据生命周期
```

### 4.4 契约的自检

```text
[ ] 前端能否只凭契约写出完整的 API 调用层，不需要问后端？
[ ] 后端能否只凭契约实现接口，不需要问前端要什么字段？
[ ] 数据端能否只凭契约设计表结构？
[ ] 错误码是否覆盖了所有已知失败路径？
[ ] 管理端越权路径是否在 Identity 契约中被明确禁止？
```

**任一为否 → 契约不完备 → 不得进入下一步。**

## 5. 第四步：垂直切片

### 5.1 什么是切片

切片是**端到端的可演示行为**，不是技术层。

```text
❌ 错误切法（按技术层）
   前端组、后端组、数据组 → 最后融合

✅ 正确切法（垂直切片）
   Slice S1  用户注册登录（UI + API + DB + 邮件/验证码适配器）
   Slice S2  核心对象的创建与列表（UI + API + DB）
   Slice S3  管理端对应的查看与管理能力
   Slice S4  文件/图片上传与访问
   ...
```

### 5.2 切片的质量标准

```text
[ ] 每一刀结束后，用户主路径必须比上一刀【多一个可演示的行为】
[ ] 一刀应在半天到两天内能演示
[ ] 小于 2 小时的改动不要单独成刀，并入相邻刀
[ ] 每刀都能独立验收，不需要等下一刀
[ ] 切片之间通过契约解耦，不通过"互相等"
```

### 5.3 切片排序

```text
- 第一刀必须是【步行骨架】：能跑通的最小闭环
  （健康检查 + 一个鉴权过的写接口 + 一张表 + 一次迁移 + 前端能打到真实 API 的页面 + 统一错误响应）
- 后续排序原则：先解锁依赖多的，先做不确定性高的（尽早暴露风险）
- 明确标出：哪些刀可以并行，哪些必须串行
```

## 6. 第五步：原子任务分解

### 6.1 严格区分三级

```text
Work Package  ── 一大块交付什么（如"完成登录能力"）
      ↓
Atomic Task   ── 最小可独立验证的工作单元（如"完成邮箱验证码登录"）
      ↓
Execution Step── 完成它具体怎么做（如"实现验证码发送"）
```

**Task 回答"要交付什么"，Step 回答"完成它怎么做"。** 不要把两者混为一谈。

### 6.2 任务卡必填字段（一个不能少）

````markdown
TASK-XXX：<任务名称>

## 归属
- 所属切片：S-N
- 来源需求：REQ-F-xxx / REQ-NF-xxx
- 来源方案：SOL-xxx / ADR-xxx

## 目标
<一句话，可验证>

## 输入
- 文档：<路径>
- 契约：<具体接口/DTO 名称>
- 前置任务：<TASK-xxx>
- 前置状态：<如"迁移 001 已合并">

## 输出
- 新增/修改的文件路径（精确到目录或文件）：
  - <path>

## Execution Steps
1. [ ] <可执行的动作>
2. [ ] ...

## 验收标准
- [ ] <可自动化检查的条件优先>
- [ ] <不可自动化的，写清人工判断标准>

## 验证命令
```bash
<可直接复制执行的命令>
```

## 证据路径
docs/06_validation/evidence/EVD-xxx/

## 允许修改
- <path pattern>

## 禁止修改
- packages/contracts/**
- database/migrations/**
- <其他>

## 依赖与阻塞
- Depends on：<TASK-xxx>
- Blocks：<TASK-xxx>
- 阻塞条件：<遇到什么就停下>

## 建议执行档位
<haiku / sonnect / opus>　理由：<一句话>

## 升级条件
<什么情况下必须升级到上一档>

## 预估规模
<小 / 中 / 大>　<是否小于 2 小时>
````

### 6.3 任务粒度标准

```text
过大的信号：验收标准超过 6 条 / 需要跨 3 个以上模块 / 预估超过 2 天
过小的信号：改动小于 2 小时 / 验收标准只有"代码能跑"

要求：
- 每个任务可以独立验证完成与否
- 每个任务不应该继续拆成多个彼此独立的交付结果
- 每个任务的所有权边界清晰（谁能改、谁不能改）
```

## 7. 第六步：依赖拓扑与并行判定

### 7.1 用机械规则判定并行（不要用主观意见）

```text
可并行 ⟺ 无共享可变状态
        ∧ 依赖的契约已冻结且机器可校验
        ∧ 文件所有权不相交
        ∧ 不共用同一迁移版本号
```

**不满足任一条 → 标为串行。**

禁止出现"这两个任务应该可以并行吧"这类无依据判断。每条并行结论必须附上它满足了哪几条。

### 7.2 输出依赖 DAG

用文本形式输出，标出：

```text
- 可并行组（同一组的任务可以同时下发）
- 必须串行的链
- 关键路径（决定整体工期的链）
- 环检测结果（不得有环）
```

### 7.3 并行纪律（写进规划，让执行者看到）

```text
✅ 允许并行：不同所有权、同一冻结契约、不改同一迁移版本号
❌ 禁止并行：
   - 同时改 contracts
   - 同时改同一张表
   - 一边改错误码、一边让前端猜字段
   - 数据端"独立完成整个数据库"（只实现本切片需要的迁移+仓储）
```

## 8. 第七步：所有权与档位分配

### 8.1 按仓库路径划分所有权（不按"前端/后端"三个产品）

```text
Agent-Contract   唯一可改 packages/contracts/ 与契约源文件
Agent-App        apps/web 或 apps/<client>
Agent-API        apps/api 的 application/interfaces
Agent-Data       database/ + infrastructure/persistence + 缓存键空间
Agent-Guard      Makefile、CI、dependency-cruiser、安全中间件测试
```

规则：

```text
- 同时最多 3 个写入 Agent
- Contract 与 Guard 不与实现并行改
- 跨所有权 = blocked，提交 ADR，不"先写了再说"
- 输出一张【所有权矩阵】：Agent × 路径，明确标注重叠处（重叠即为规划缺陷，必须消除）
```

### 8.2 档位分配

按「决策的不可逆性 + 影响范围」分配，不按步骤号：

| 档位 | 适用 | 禁止 |
|---|---|---|
| `fable`（最强最贵） | 需求范围终裁、推翻已冻结契约、全局性冲突 | 高频任务（极度烧钱） |
| `opus` | 架构 ADR、契约语义、跨模块集成仲裁、安全审查、高风险 review | 写样式、写样板 |
| `sonnect`（主力） | 原子任务实现、单测、组件、CRUD、迁移脚本、E2E 脚本 | 独自做架构决策 |
| `haiku`（最廉） | 格式化、重命名、填模板、日志归类、索引更新 | 改领域规则 |

**默认档 = opus。** 不要默认用 sonnect，也不要默认用 fable。

### 8.3 成本预算表

为每个切片输出：

```text
| 切片 | 任务数 | haiku | sonnect | opus | fable |
|------|--------|-------|---------|------|-------|
| S1   | 6      | 1     | 4       | 1    | 0     |
...

券制度：
  opus   每切片 ≤3 次（切片前契约审 / 卡住升级 / 高风险 review）
  fable  每切片 ≤1 次（仅在需要动需求或已冻结契约时启用）
  超出需人批准
```

### 8.4 熔断规则

```text
同一任务连续 2 次验收失败 → 停止改代码
  → 改为：重写任务书 / 升级档位 / 标记 blocked
禁止换提示词硬撞第 3 次（隐性烧钱最大的洞）
```

## 9. 第八步：基线指标与验收体系

### 9.1 基线指标（性能先行的前提）

```text
- 定义 3–5 个【用户可感】的核心操作
- 为每个操作定义可测量的指标（延迟 / 包体积 / 查询次数 / 渲染次数）
- 每个指标必须先证明：这个数字降了，用户可感耗时也降
  证明不了 → 下线，不让它成为优化目标
- 给出首次测量值（基线），没有基线的指标不算指标
```

**没有基线数字，后续禁止任何"优化"任务。**

### 9.2 完成定义（全项目唯一口径）

```text
Done ≠ 模型说"完成"   ≠ 代码写完   ≠ 推送到 GitHub

Done =
    所有权内 diff 符合任务
  ∧ 验收条目逐条有结果
  ∧ 自动测试或脚本可复现
  ∧ evidence 能让一周后的人复现，不用问原作者
  ∧ make guard 通过
  ∧ 无新增同类错误记录
  ∧ 未修改冻结契约（除非本任务就是改契约）
```

### 9.3 防自证循环

```text
禁止：同一个 Agent 写验收标准 + 执行 + 判定自己通过

要求：
  验收标准由规划阶段确定（即你，现在）
  执行由开发 CLI 完成
  判定由独立验证者完成，且只看 diff + 运行结果
  独立验证者只输出 PASS / FAIL / UNKNOWN，不输出长篇解释
```

### 9.4 必须建立的自动化守卫

```text
- 契约测试（从契约自动生成）
- 架构边界检查（ESLint 模块边界 / dependency-cruiser）
- 根目录污染检查
- 密钥扫描
- 相关单测 / 集成测
（以上作为 PR 合并的硬门禁，任一不过不得合并）
```

## 10. 输出格式（严格遵守）

按以下顺序输出。不要省略任何一节；某节无内容时写"无"并说明为什么。

```text
1.  规划快照
2.  事实基线（含文档与代码不一致清单）
3.  需求基线复核
    3.1 复述与拆解
    3.2 MUST / SHOULD / COULD / MUST NOT
    3.3 冲突清单
    3.4 未知登记册（BLOCKING / NON_BLOCKING）
    3.5 隐含要求与前置条件
4.  契约冻结包（六份，全量内容）
5.  数据模型基线（含迁移版本号编排）
6.  垂直切片清单（含排序与理由）
7.  原子任务卡全集（每张卡含全部必填字段）
8.  依赖 DAG（可并行组 / 串行链 / 关键路径 / 环检测）
9.  所有权矩阵（Agent × 路径，标注重叠）
10. 档位分配与成本预算表
11. 基线指标（含首次测量值）
12. 风险清单 / 未决问题 / 待裁决清单
13. 落盘清单（写入了哪些文件，路径 + 用途）
```

## 12. 自检清单（输出前逐条核验）

```text
需求
[ ] 每条 MUST 都能改写成一句可验证的话
[ ] 冲突已全部列出，没有静默替用户决定
[ ] BLOCKING 项已列出并给出条件方案，未擅自假设
[ ] 未为凑数伪造需求或方案

契约
[ ] 六份契约齐全，且是机器可校验的形式
[ ] 指定了唯一源，没有多源并存
[ ] 前端 / 后端 / 数据端三方都能只凭契约独立开工
[ ] 错误码覆盖所有已知失败路径
[ ] 管理端越权路径已被明确禁止

切片与任务
[ ] 按垂直切片划分，不是按技术层
[ ] 每刀都能独立演示、独立验收
[ ] 第一刀是步行骨架
[ ] 每张任务卡字段齐全（16 项一个不少）
[ ] 每张任务卡都有可执行的验证命令
[ ] 每张任务卡都有明确的允许/禁止修改路径
[ ] 每个任务都能反向追溯到一条需求

依赖与并行
[ ] 依赖图无环
[ ] 每条并行结论都附了机械规则的满足依据
[ ] 关键路径已标出
[ ] 所有权矩阵无重叠

资源与风险
[ ] 每个任务都标注了建议档位与理由
[ ] 成本预算表已给出
[ ] 基线指标有首次测量值，或明确标注"尚无基线"
[ ] 风险 / 未决 / 待裁决已分开列出

纪律
[ ] 未修改任何业务代码
[ ] 未输出无证据的绝对结论
[ ] 未用"最佳实践""行业惯例"替代本项目证据
[ ] 所有未验证项都已显式标注
```

**任一未过 → 修正后重新自检，不得带着未过项输出。**

## 13. 绝对禁止

```text
1.  未复核需求就直接开始规划
2.  未建立事实基线就断言代码现状
3.  把文档描述当成当前实现
4.  把未验证的推断写成事实
5.  为凑够两个方案而伪造不可行方案
6.  用专家名望 / 行业惯例提高方案权重
7.  对没有数据支撑的指标进行伪精确量化
8.  缺少基线就排出"优化"任务
9.  按技术层切片（前端组/后端组/数据组）
10. 任务卡缺少验收标准或验证命令
11. 并行结论没有机械依据
12. 所有权矩阵存在重叠却不处理
13. 提前为"未来可能需要"设计表或建目录
14. 遇到信息缺失时擅自假设并继续
15. 只输出总结而不提供证据来源
16. 只论证正面理由而不找反证
17. 输出"绝对正确""一定成功"等无证据结论
18. 修改任何业务代码
19. 把模糊回复当作执行授权
20. 最终规划无法反向追溯到真实需求却宣布完成
```
