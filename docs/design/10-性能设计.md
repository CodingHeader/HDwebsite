> 文档体系关联：P1~P7 与性能预算 ↔ REQ-NF-001；验证口径见 06_validation/validation-plan.md｜总索引：README.md §0

## 1. 现状性能措施

| 层 | 措施 | 说明 |
| --- | --- | --- |
| 请求级缓存 | React `cache()`（settings） | 同一请求内 settings 只查一次 DB |
| 查询并行 | `Promise.all([findMany, count])` | 列表页两查合一往返 |
| 服务端分页 | page/limit + skip/take | 避免全表拉取 |
| 索引 | 高频列全覆盖（status/sort/slug/createdAt/parentId/type…） | SQLite 单文件读性能良好 |
| 图片处理 | sharp 缩略图三级（100/300/800）+ progressive jpeg | 列表用小图、详情用大图可分流 |
| 输出 | `output: "standalone"` | 部署体积与启动开销小 |
| 连接池 | Prisma + libsql adapter 单例 | 复用连接 |
| AI 容错 | 88s 长超时承受冷启动 + 15s 短重试 | 换取首次可用性（非性能最优解） |
| 关闭项 | `optimizeCss:false`、`cssChunking:false` | 规避构建器兼容问题，牺牲部分 CSS 优化 |
| 按需编译 | onDemandEntries（maxInactiveAge 25s / pagesBufferLength 4） | dev 阶段内存控制 |

## 2. 性能风险点

| # | 风险 | 位置 | 缓解 |
| --- | --- | --- | --- |
| P1 | SQLite 单写者 | 全站 | 低并发场景够用；写竞争加剧时迁 PostgreSQL |
| P2 | 详情页 viewCount 同步自增 | articles/[id] | 高流量改异步批量（UserAction 聚合定时回写） |
| P3 | 知识检索 contains 全表扫 | chat/completion | 知识量增长后切 FTS5 / 向量库 |
| P4 | 无页面级缓存/CDN | 全站 | 内容型页面可加 ISR 或 Cache-Control（重构期评估） |
| P5 | remotePatterns `https://**` | next.config | 外域图片直出有安全/性能风险，收紧白名单 |
| P6 | AI 非流式 | chat/completion | 用户等待感强 → SSE 流式（N9） |
| P7 | 上传原图落 public | upload-service | 与 standalone 同步机制耦合，量大后迁对象存储 |

## 3. 重构期性能预算（新增功能约束）

| 模块 | 预算 |
| --- | --- |
| 采集任务 | 每源限速（≥2s 间隔）、夜间窗口执行、失败限次 |
| 自动发布 | 批量发布串行 + 间隔，避免触发微信频率限制 |
| 知识检索 | 命中 ≤6 chunk、注入 token 上限（现状 take 6，保持） |
| 邮件 | 异步队列发送，不阻塞主请求 |
| 公众号同步 | access_token 缓存至过期前 5 分钟，减少往返 |
| LLM 调用 | 网关统一超时（默认 30s 可配）+ 并发上限 |

## 4. 补充（2026-10-10 第二轮实测）

| # | 新识别风险 | 缓解 |
| --- | --- | --- |
| P8 | useSettings 每个客户端组件挂载独立 GET /api/settings（全量 ~40 项），无共享缓存/请求去重 | 根布局 SSR 一次性注入 Settings 传 props，或模块级 Promise 单飞（single-flight）缓存 |
| P9 | GET /api/settings 每请求全表查 Setting + Registry 合并，无 HTTP 缓存头 | 公开设置变更频率极低 → 加 `Cache-Control: s-maxage` 或构建期快照 |
| P10 | AI 非流式 + 88s 超时，前端等待不可预期 | N9 落地 SSE 流式 + llm-gateway 统一 30s 超时（→ 16 §7.2） |
