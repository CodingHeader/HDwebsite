## 1. 统一响应包（lib/api-response.ts）

```ts
interface ApiResponse<T> { code: number; data: T; message: string }
```

| 工厂函数 | code | 默认 message | HTTP 状态 |
| --- | --- | --- | --- |
| success(data, msg) | 200 | 操作成功 | 200/201 |
| error(msg, code=400) | 400 | — | 400/500 |
| unauthorized | 401 | 未授权访问 | 401 |
| forbidden | 403 | 权限不足 | 403 |
| notFound | 404 | 资源不存在 | 404 |
| serverError | 500 | 服务器错误 | 500 |

约定：**HTTP 状态码与业务 code 并行设置**（`NextResponse.json(error(msg), { status: n })`），前端可任选其一判断。

## 2. 列表分页契约

```json
{
  "code": 200,
  "data": {
    "list": [ ... ],
    "pagination": { "page": 1, "limit": 10, "total": 87, "totalPages": 9 }
  },
  "message": "获取文章列表成功"
}
```

- 查询参数约定：`page`(默认1)、`limit`(默认10)、`keyword`（title/content/excerpt OR 模糊）、各业务过滤列。
- 排序约定（文章）：isTop desc → publishedAt desc → createdAt desc。

## 3. 错误响应细则

| 场景 | 响应 |
| --- | --- |
| zod 校验失败 | 400 + 首条 issue.message（中文文案内置 schema） |
| 未带 token / token 失效 | 401 + "未提供认证令牌"/"认证无效或已过期" |
| 权限不足 | 403 + "权限不足：需要 article:create" |
| slug 重复等业务冲突 | 400 + 具体中文提示 |
| 上游 AI 失败 | 502/503 + "AI 服务错误：{status}" / "尚未配置可用的 AI 模型…" |
| 未捕获异常 | 500 + "XX失败"（不泄堆栈） |

## 5. 前端消费方式

- 后台：`manager-fetch.ts` 统一解包（非 200 code 抛 message）→ zustand/组件态。
- 前台页面：服务端直查 DB，不经 HTTP，无响应包问题。
- 客户端组件（报名/AI 聊天）：直接 fetch + 判 `code===200`。

## 7. 补充（2026-10-10 第二轮实测）

- **契约不严格实例**：GET /api/settings 数据形态为对象 `{key:value}`，但 useSettings 同时兼容数组与对象两种格式——契约应收紧为单一形态并出 TS 类型（`Record<string, string>`），消费方删除兼容分支。
- **权限响应缺口**：POST /api/settings 仅登录校验、无权限点 → 403 分支在部分写接口缺失，重构期统一走 requirePermission 补齐。
- 新增接口族（§6 表）建议重构期随实现同步产出 OpenAPI/类型描述，前后端同源。
