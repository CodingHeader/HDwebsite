# ADR-035：通知可靠性——静默时段生效 + 跨进程原子去重 + 邮件脱敏

- 状态：已接受（2026-10-20）
- 所属卡：B-06（通知可靠性）
- 影响范围：`src/lib/notify-gateway.ts`、`src/app/api/notify-rules/[id]/route.ts`
- 替代/补充：ADR-004（邮件单点）、ADR-027（契约冻结面纪律）

## 背景

P06 评审遗留三项通知可靠性问题：

1. **静默时段未生效**：`NotifyRule.quietHours` 列已在 `prisma/schema.prisma:956` 存在、E-02 页面已可配置，但后端从未消费（B 域实测确认）。
2. **去重非原子**：`notify-gateway.ts:59-63` 采用"查最近记录 → 建记录"，串行化仅进程内（`aggregateChain`），两进程并发时可能都通过检查。
3. **堆栈未脱敏**：错误正文可能包含 token/key/password 形态字串（P06-verify:90）。

## 决策

### 1. 静默时段生效（规则级优先）

- 判定基于 `Intl.DateTimeFormat` + `timeZone: "Asia/Shanghai"`（上海无夏令时，分钟数 0..1439 可靠）。
- 优先级：规则级 `rule.quietHours` > 全局设置 `notifyQuietHours` > 无静默。
- 语义：`start<=end` 同日内（`[start, end)`）；`start>end` 跨夜（如 22:00→07:00）。
- **无效时刻（不满足 `^([01]\d|2[0-3]):[0-5]\d$`）按"无静默"处理并 `console.warn`**（DR-14）。
- 静默内事件照常建 `NotifyRecord(status=deferred)`，只不发信；`flushDeferred()` 在时段结束后将其转 `pending` 并投递。
- 测试需要可控时钟：`__setNotifyClock(provider|null)` 注入 `nowProvider`（`vi.setSystemTime` 不改 `Intl` 时区结果）。

### 2. 去重跨进程原子化

- **不改 schema**（迁移冻结）。用单条 SQL：`INSERT INTO "NotifyRecord" (...) SELECT ... WHERE NOT EXISTS (SELECT 1 FROM "NotifyRecord" WHERE "event"=? AND "subject"=? AND "createdAt">=datetime('now','-10 minutes')) RETURNING "id"`。
- SQLite 单语句原子：两进程并发时仅一个的 WHERE 为真，另一 `RETURNING` 空 → 丢弃。
- **去重键** = `event` + `subject` + 10 分钟窗。`subject` 渲染后含 `{title}`，`title` 承载"路由/任务名"标识（`notifyApiError` → `方法 路由`；`notifyJobFailed` → 任务名），满足卡定义"事件 + 路由/任务名 + 10 分钟窗"。
- **时间边界必须用 SQL 内 `datetime('now','-10 minutes')`**，不能绑定 Date：`createdAt` 由 `CURRENT_TIMESTAMP` 写入（`YYYY-MM-DD HH:MM:SS`，UTC），绑定 ISO（含 `T`）会因字典序比较误判。
- 进程内 `aggregateChain` 保留为同进程兜底；跨进程由 SQL 原子保证。

### 3. 邮件正文脱敏

- `sanitizeSensitive(text)`：`password|passwd|secret|token|api_key|access_token` + `=/:` 后的值、`sk-` 前缀、≥20 位字母数字下划线连字符串 → 替换为 `***`。
- 对 `subject` 与 `content` 都应用（投递前）。

### 4. `notify-rules` PATCH 接收 `quietHours`

- 契约 `notifyRuleUpdateSchema.quietHours`（CCR-1）已在 `contracts/resources.ts:282` 定义；路由此前未写库。本次补上 `quietHours` 写入分支：`null` → 清空；对象 → `JSON.stringify`；未提供 → 不更新。

## 行为等价性与回归

- 非聚合事件、非静默时段：`notifyEventInner` 行为与原来一致（查规则 → 模板 → 收件人 → 建 pending → 投递）。
- `deliver`、退避、`notifyRetryScan` 主循环不变；`notifyRetryScan` 仅在开头插入 `await flushDeferred()`。
- 聚合事件的"查最近"分支已移除，由原子插入替代；语义上仍"10 分钟只 1 条"。
- **越界检查**：未触碰 `src/contracts/**`、`prisma/`、`package.json`、vitest/Playwright 配置；未新增调度任务（jobs 属 D 线）。

## 验证

- `lane-b/notify.test.ts` 9 用例：静默内 deferred / 结束后补发 / 无效时刻按无静默 / 并发聚合 1 条 / 同窗不同 detail 1 条 / 同窗不同 title 各 1 条 / 脱敏 / PATCH quietHours 回读 / PATCH null 清除。
- 门禁四连：lint 0 errors/54 warnings（基线）、tsc exit 0、test 62 files/779 passed、build exit 0。

## 后果与局限

- 去重键含 `subject`：若某事件 title 含动态时间（如通知标题带时刻），同窗内不会误合并——实际 `notifyApiError`/`notifyJobFailed` 的 title 均为固定路由/任务名，稳定。
- `flushDeferred` 挂在 `notifyRetryScan` 内，未新增独立任务；若需要更高频补发（如静默结束后立即），需 D 线新增任务（越界，未做）。
- "5 次异常只 1 条"：卡验收原文为 5 次，实测用并发 2 次 + 同窗多 detail/title 组合验证等价性；未虚报 5 次。
