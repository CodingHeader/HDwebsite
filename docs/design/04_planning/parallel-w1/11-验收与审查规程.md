# 11 验收与审查规程（全项目唯一口径）

## 1. 完成定义（规划总指令 §9.2）

```text
Done = 所有权内 diff 符合任务卡
     ∧ 验收条目逐条有结果（PASS / FAIL / UNKNOWN）
     ∧ 自动测试或脚本可复现
     ∧ 证据能让一周后的人复现，不用问原作者
     ∧ 守卫通过：lint / typecheck / 单测 / build（+ 涉及前台引用文件时 visual，涉及页面或接口时 e2e）
     ∧ 无新增同类错误
     ∧ 未修改冻结面（契约、迁移、依赖、配置、他线文件）
```

“模型说完成”“代码写完”“推上 GitHub”都不等于 Done。

## 2. 三权分离（防自证循环）

| 角色 | 谁 | 做什么 | 不做什么 |
| --- | --- | --- | --- |
| 规划者 | 本规划（已写定验收标准） | 定标准、定所有权 | 不执行、不判定 |
| 执行者 | 每条线一个开发 CLI | 按任务卡实现、写证据、提交到 lane 分支 | 不改验收标准、不给自己判 PASS |
| 独立验证者 | 另开一个会话，使用《提示词-独立验证者》 | 只看 `git diff <起点>..<终点>` 与命令输出，逐条给 PASS/FAIL/UNKNOWN | 不看执行者自述、不改代码、不写长篇解释 |
| 集成者（主审） | 我（Hark）或用户指定的 opus 会话 | 裁决契约变更请求、合并、终审 | 不替执行者补代码 |

## 3. 每张卡的验收流程

1. 执行者完成卡 → 跑卡内验证命令 + 通用门禁 → 证据写到 `docs/design/06_validation/evidence/<W0|W1-X|W2>/<卡号>/` → 提交。
2. 每完成一个工作包（WP）提交一次验证请求；独立验证者输出 `<卡号>-verify.md`：
   - 第一步固定检查路径：`git log --first-parent --no-merges --name-only --format= <起点>..HEAD | sort -u` 必须全部落在卡的“允许修改”内（只看本线非合并提交；合并进来的 M1、已批准 CCR 不计入）。越界 = FAIL，不再看功能。
   - 第二步逐条执行验收命令，记录 exit code 与关键输出行。
   - 第三步回归：通用门禁；改了前台引用文件 → visual；改了页面/接口 → e2e。
3. 同一卡连续 2 次 FAIL → **熔断**：停止改代码，执行者写《失败分析》，集成者决定重写卡/升级档位/标 blocked。禁止换个说法硬撞第 3 次。

## 4. 契约变更请求（Wave 1 内唯一合法的跨线通道）

执行者遇到以下情况必须停止该子项并提交请求，不得“先写了再说”：

- 需要改 `src/contracts/**`、`prisma/schema.prisma`、迁移、依赖、vitest/playwright 配置；
- 需要改别的线拥有的文件（例如 B-06 需要 D 线 jobs/index.ts 注册一行）。

请求格式（写入 `docs/design/06_validation/evidence/W1-X/CCR-<序号>.md`）：

```text
CCR-<线>-<序号>
- 提出者 / 任务卡：
- 需要改的文件与精确改动（diff 草案）：
- 为什么现有契约不够（证据：文件:行 / 失败的测试）：
- 影响哪些线：
- 不改的替代方案及代价：
```

集成者裁决：批准 → 在 upgrade 上单独提交（`chore(CCR-x): …`）→ 通知受影响线 `git merge upgrade`；驳回 → 给出替代做法。影响 ≥2 条线的请求须 opus 审。

## 5. 合并规程（W2-01）

- 合并顺序：**D → B → C → A → E**（基础设施先、消费方后；A 在 M1 已部分合入，此处合入 A-05/A-06/A-08）。**2 名执行者（已定）**：先合 `lane/backend`（B→C→D），再合 `lane/ui`（A→E）；两人互为独立验证者。
- 每次合并前：该线所有卡的 verify 均 PASS；合并后跑 GATE + visual + e2e，日志入 `evidence/W2/merge-log.md`。
- 冲突只允许出现在证据文档；出现在代码文件 = 所有权矩阵缺陷，停止合并并回到规划修正。

## 6. 守卫（PR/合并硬门禁）

| 守卫 | 命令 | 首次就绪 |
| --- | --- | --- |
| 契约测试（全路由自动发现） | `npx vitest run tests/contract` | W2-02（守卫不与实现并行，§8.1） |
| 架构边界（src/lib 不得 import @/app；路由内不得定义请求 DTO） | `npm run lint`（直接 error） | W2-08 |
| 根目录污染 | `node scripts/check-root.mjs` | W2-09 |
| 资源引用完整 | `node scripts/check-assets.mjs` | W2-09 |
| 密钥扫描 | `git diff <起点>..HEAD \| grep -nE "sk-[A-Za-z0-9]{20,}\|ghp_[A-Za-z0-9]{20,}\|github_pat_\|-----BEGIN [A-Z ]*PRIVATE KEY"` 为空 | 每次验证 |
| 单测 / 构建 / 视觉 / E2E | GATE、`npm run test:visual`、`npm run test:e2e` | 已有 |

## 7. 安全铁律（每份提示词都包含）

1. 不在聊天、日志、文件名、计划、证据、提交信息中明文出现私钥、token、密码、API key。
2. 推送凭据由用户在本机配置（credential helper 或权限 600 的凭据文件），执行者不接触、不搜索、不打印；临时文件用完立即删除。
3. remote URL 不得含凭据：`git remote get-url origin | grep -qE 'https://[^/]*@'` 必须无输出（SSH 地址正常）。
4. 不提交 `.env*`、`prisma/*.db`、`backups/`、`data/`、运行时上传。
5. 提到凭据时只写“推送凭据”“访问令牌”等泛称。
