# 经验教训

## LL-001：并发会话双文档体系冲突（C7 教训）

- **事件**：docs/get/ 同时出现本会话中文体系与另一会话 14 个英文草稿，内容模板化、非项目实证。
- **教训**：同一目录多会话产出 = 权威歧义。规则：**单会话产出原则**；发现外部并存文件先登记冲突（C7 模式）再询问，不擅自合并。
- **应用**：ADR-007；RISK-004 已缓解。

## LL-002：文档断言必须代码实证（UserAction 案例）

- **事件**：早期文档曾写"FloatingContact 点击即上报 UserAction"，代码核验后证明前台零调用（死管道）。
- **教训**：行为类断言必须 grep 调用方实证；只有定义不算存在。
- **应用**：05-交互 §4 证据表；验证计划 G 类走查含操作实证。

## LL-003：半成品识别法 = 查调用方而非查定义

- **事件**：ElementConfig、starters 均有完整定义与配置界面，但前台从不渲染。
- **教训**：模型定义 + 管理页 ≠ 功能存在。识别半成品三步：定义 → 配置方 → 渲染方，三环缺一即死。
- **应用**：08-复用 §8；REQ-F 系列验收条件均写到"端到端可见"。

## LL-004：安全工具必须单一入口

- **事件**：articles 内容有净化，services/[slug] 直写 dangerouslySetInnerHTML 绕过净化。
- **教训**：横向复制功能时净化/鉴权/加密易漏。约束：净化收敛为单点（SOL-001），新增渲染路径强制接入。
- **应用**：REQ-NF-002；M1-4 验证项。

## LL-005：泛化模板判别（对照 C7 英文草稿）

- **信号**：内容与项目无关的通用章节、无代码坐标、无项目专有名词。
- **处置**：标记疑似外部产物 → 登记 → 询问 → 决策后处置（删除/归档）。
- **应用**：本次直接删除（ADR-007）；未来先入 09_archive 待确认。

## LL-006：决策先行消除返工

- **事件**：8 项冲突若在开发中暴露（如 News 表迁移做到一半才问），返工成本倍增。
- **教训**：拿不准即问（Q&A 多轮至 100% 置信），决策即时 ADR 化。
- **应用**：talk.md Q1~Q3 完整留存；ADR-001~008 与需求/方案/验证全链路贯通。

## LL-007：规范落地要裁剪而非照搬

- **事件**：项目完整文档体系.txt（v1.1，55+ 节）若全量照搬将产生大量空壳文档与空目录。
- **教训**：按有用即取、暂无用即缓建裁剪——模板可裁节（需求 11 节→9 节）、目录可缓建（09_archive/tasks/evidence），但结构性规则（ID/状态/追溯/DoD）全量保留。
- **应用**：document-standard.md 即裁剪落地版；后续扩展以它为唯一口径。

## LL-008：计划表的 done 必须以文件实态为准

- **事件**：current-plan 本轮表曾预标 TN-009~014、LL-007、README 编号对照为 done，但文件实际未落盘（会话中断所致）；Q7 轮核查发现并补齐。
- **教训**：计划状态 ≠ 文件实态。收口前必须以 glob/grep/重读核对声称完成的每一项。
- **应用**：本轮收口执行了全量核查（ADR 文件存在性、编辑落盘、编号引用一致性）。

## LL-009：git add 前必须核验增量文件清单

- **事件**：第八轮提交（33eef58）时 `git add docs/get` 意外带入并发出现的 new-features.md（本会话未创建），提交后核对提交清单才发现，遂核验处置。
- **教训**：提交前先 `git status` 对照本轮预期改动清单；出现非预期新文件 → 暂不提交 → 读内容核验 → 一致则注册收录、冲突则按 C7 模式（LL-001/ADR-007）登记询问，不擅自合并或删除。
- **应用**：new-features.md 核验与 ADR-001~020 一致后已注册（README §1 / document-index §10 / project-map §1·§3），文件头映射行笔误修正。
