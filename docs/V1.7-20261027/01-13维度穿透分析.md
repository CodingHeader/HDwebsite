# 01 · 十三维度穿透分析

> 每维给出：结论 → 证据（file:line 或命令输出）→ 反向检验（这个结论可能错在哪）→ 判定。
> **优先自我否定**：凡我先想到的结论，先找一遍反证。

---

## 维度 1 · 需求

**结论**：需求层没有缺失，但**需求到实现的验证口径有缺陷**。

**证据链（三层）**：
1. `parity-matrix.md:26` —— `missing（0 行） | 0`
2. `parity-matrix.md:50` —— A1 行判 `present`，理由是「11 个区块组件**全部存在**」
3. 实测：11 个组件确实都存在（`ls src/components/web` 26→30，原版有的全在）

**但**：判据是「文件存在」。第 3 层证据证明文件在，却证不出**能力等价**。第 4 层（`00 §八`）显示 9 个组件丢了 props。

**反向检验**：会不会「props 少了但能力通过别的路径保留了」？
→ 查 `page.tsx:66,75,93,102,111,120,129,138,147` 九处调用，全部**只传必需参数**，没有任何一处传 `showOverlay`/`bgImage`。能力确实没有替代路径。

**判定**：需求覆盖面无缺失；**验证口径需修正**（组件存在 ≠ 能力对等）。

## 维度 2 · 前端

**结论**：视觉呈现不变，但**配置化能力系统性退化**。

**证据**：

| 组件 | 原版 | 新版 | 证据 |
|---|---|---|---|
| TopBanner | `:11 showOverlay` `:10 bgImage` `:48 {showOverlay && (` | `:6-9` 只 2 props | 原版 `:30-46` 有 bgImage→style 逻辑 |
| NewsCenter | `:18` `:63 {showOverlay && (` | `:44` 只 1 prop | 标题栏恒显 |
| FourCards | `:20-25` 7 个 CardData 字段 | `grep` 0 命中 | 卡片背景图/显隐/对齐全丢 |
| Banner | 14 props 含 `showExtraBtn` | 13 props | 第二按钮能力丢失 |
| 其余 6 组件 | 均含 `showOverlay` | 均无 | `for c in ...; grep -q showOverlay` → 8/9 无 |

**反向检验**：新版是否用统一的「区块启停」（`resolveHomeBlocks`）替代了组件级 `showOverlay`？
→ 部分成立：`block-registry.ts` 的 `resolveHomeBlocks` 确实能控制**整块**显隐（`:65` `if (tb.block.status !== "active" \|\| config.enabled === false) continue`）。
→ 但**不能**替代组件内部的 `showOverlay`（控制的是区块内标题栏，不是整块）。

**判定**：整块启停 ✅ 有（且强于原版）；组件内部细粒度配置 ❌ 丢失。

## 维度 3 · 后端

**结论**：后端**大幅增强**，但存在 1 处页面级断链。

**证据**：

| 项 | 原版 | 新版 | 说明 |
|---|---:|---:|---|
| API 路由 | 60 | **126** | 2.1× |
| 统一 handler | 1（`api-auth.ts`） | 15 导出 / **52 处 `withApi(`** | 请求包装标准化 |
| 旧路径兼容 | 无机制 | `api/ai-config/route.ts` 307 映射表 | 渐进式迁移 |
| `/manager/ai-config` 页面 | 有 | **无路由、无 redirect** | `ls src/app/manager/ai-config` → 不存在；`grep ai-config next.config.ts` → 空 |

**反向检验**：`/manager/ai-config` 是否由 `llm-providers` 完全替代，因此不该保留？
→ 部分成立：功能上 `llm-providers` 更全（多模型优先级/兜底/余额）。
→ 但**页面层无任何跳转**，原版书签打开会 404。API 层做了兼容（307），页面层没做 —— **不对称**。

**判定**：后端主体 ✅ 强于原版；`/manager/ai-config` 缺兼容重定向（P1）。

## 维度 4 · 数据

**结论**：模型 +14，两次模型变更中**一次有 ADR、一次无 ADR 且丢字段**。

**证据**：

| 变更 | ADR | 字段承接 | 判定 |
|---|---|---|---|
| `News` → `Article.channel` | ✅ `ADR-001-News并入Article.md:21` | `schema.prisma:194 channel` | 合法 |
| `AIConfig` → `LLMProvider` + `ChatScene` | ❌ 无 ADR | 12/14 字段有承接，**`userPrompt` 无** | 不规范 |
| `HomeCard.backgroundImage` | ❌ 无记录 | **模型无此字段** | 丢失 |

**证据细化**：
```bash
# 原版 HomeCard 有
prisma/schema.prisma (原版)  backgroundImage String? // 卡片背景图片URL

# 新版无
sed -n '/^model HomeCard/,/^}/p' (新版)  # id/title/subtitle/icon/href/gradient/hoverGradient/shadow/sort/status
```

**反向检验**：`userPrompt` 是否被 `ChatScene` 的某字段替代？
→ `grep -rn "userPrompt" src/` 在新版 **0 命中**。`ChatScene` 只有 `systemPrompt`/`greeting`，无 user prompt 模板。**确认丢失**。

**判定**：`userPrompt`（P1）、`HomeCard.backgroundImage`（P1）为真缺口；News 合并合法。

## 维度 5 · 交互

**结论**：管理端交互**全面重做且远强于原版**；前台交互存在 1 处退化。

**证据**：

| 项 | 原版 | 新版 |
|---|---|---|
| 原生 `<Table>` 使用 | **22 个 manager 页** | 0（全走设计系统） |
| 五态组件 | 无（无 `EmptyState`/`ErrorState`/`Forbidden`） | **8 个**（`src/components/manager/feedback/`） |
| 键盘快捷键 | 无 | `FormDialog.tsx:88-90` Ctrl/⌘+S/Enter |
| 移动端卡片 | 无 | `DataTable.tsx:8` 声明 <md 切卡片 |
| 微信二维码浮层 | 配置驱动（`FloatingContact.tsx:64 wechatQrCode ?`） | **写死文字占位**（`FloatingContact.tsx:83` `<span>微信二维码</span>`） |

**反向检验**：二维码占位是否因为「用户还没提供二维码图片」而临时留白？
→ 有可能。但原版是**配置驱动**（有则显示、无则隐藏），新版是**硬编码占位**（永远显示灰框）—— 即使未来提供图片也无处配置。这是能力退化，不只是数据缺失。

**判定**：管理端交互 ✅ 大幅增强；前台二维码配置 ❌ 退化（P1）。

## 维度 6 · 逻辑

**结论**：配置驱动逻辑**强于原版**，但过滤逻辑有丢失。

**证据**：

| 逻辑 | 原版 | 新版 |
|---|---|---|
| 首页区块解析 | `(web)/page.tsx` 384 行，硬编码 if/else 读 settings | `block-registry.ts` `resolveHomeBlocks()` 读 TemplateBlock + 注册表合并 + 缓存 + 失败回落默认 |
| 缓存失效 | 无 | `cache-tags.ts` 11 个 tag，`invalidateWebContent` 按模型失效 |
| 读库失败兜底 | 无（页面直接抛） | `:57-60 catch → return defaults()` |
| 内容过滤 | `showcase.ts` 三组守卫（毒文本/破图/乱码） | **无**（但原版调用点也仅测试） |

**反向检验**：新版无毒文本过滤是否会导致脏数据上首页？
→ 检查新版数据源：`HomeCard`/`Campus`/`Gallery` 均来自 DB，由管理端录入。若录入端已有校验则无需展示端过滤。
→ 实测 `grep -rn "xgnedu" src/` 命中 1 处 —— `ApplyClient.tsx:277` 的**话术文案**（"加微信 xgnedu 咨询"），是业务文案不是脏数据。**说明数据已洁净，过滤可省**。

**判定**：区块解析逻辑 ✅ 显著增强；毒文本过滤丢失属 **P2**（原版也已边缘化）。

## 维度 7 · 组件

**结论**：设计系统从 0 建成，但首页区块组件 props 被削。

**证据**：

| 项 | 原版 | 新版 |
|---|---|---|
| 管理端设计系统 | `src/components/ui`（shadcn 原件 11 个） | `src/components/manager/ui` + `feedback` + `shell`，`mgr-*` 令牌 |
| 首页区块组件 | 26 个 | 30 个（+ChatWidget/MarkdownRenderer/UserActionTracker/TopEntranceSection） |
| props 完整度 | 见 `00 §八` | 8/9 组件丢失 showOverlay |

**反向检验**：削 props 是否为了「减少复杂度/降包体」的有意决策？
→ 查 changelog：`docs/design/07_release/changelog.md` 中无任何「裁撤组件配置能力」记录。
→ 查 ADR：`grep -rln "props\|showOverlay" decisions/*.md` 无命中。
→ **无记录 → 属无意识丢失**，非有意决策。

**判定**：设计系统 ✅ 从无到有；区块 props ❌ 无记录裁撤（P0/P1 待定级）。

## 维度 8 · 复用

**结论**：1 处重复实现，1 个工具模块整体缺失。

**证据**：

```bash
# 重复实现
src/app/(web)/gallery/page.tsx:19   async function localImageExists(url: string) {
src/components/web/data/home.ts:17  async function localImageExists(url: string) {
# 原版是单一实现
原版 src/lib/showcase.ts:84         export async function localImageExists(url: string)
```

**反向检验**：是否存在循环依赖导致不能共用？
→ 两处实现均在 server component / data 层，`src/lib/showcase.ts` 是纯 Node API（`fs/promises`），无 React 依赖。**可共用，无技术障碍**。

**判定**：`localImageExists` 重复（P1，维护成本）；`showcase.ts` 缺失但功能可省（P2）。

**证据**：

**判定**：拓展 ✅ 6 个新域真实落地。

## 维度 10 · 性能

**结论**：新版引入缓存体系（原版为 0），但动态路由占比 100%。

**证据**：

| 项 | 原版 | 新版 |
|---|---|---|
| `unstable_cache` 调用 | **0** | **17** |
| 缓存 tag | 无 | 11（`cache-tags.ts:11 WEB_TAGS`） |
| `force-dynamic` 路由 | 1 | **126（全部）** |
| 前台首屏 | server component | server component（相同） |

**反向检验**：126 个 API 全部 `force-dynamic` 是否意味着缓存白做？
→ 不成立。`force-dynamic` 针对 **API 路由**（必须实时），缓存作用于**前台页面数据**（`resolveHomeBlocks` 等）。两者不冲突。
→ 但 `force-dynamic` 100% 覆盖说明 API 层**无 HTTP 缓存**，高并发下压力全压 DB。这是可优化点，但**原版同样无缓存**，不属退化。

**判定**：性能 ✅ 增强（引入缓存）；API 层无 HTTP 缓存属 **P2 优化项**，非对等缺口。

## 维度 11 · 配置

**结论**：键数 80→85（+5），但**8 个有消费点的键消失**。

**证据**：见 `00 §四`。真实缺失 8 项，每项都有原版消费点（file:line 已列）。

**反向检验**：这 8 个键是否因为对应组件 props 已删而被「顺带清理」？
→ 正是如此。但**因果颠倒**：正确顺序应是「先决定是否保留能力，再删 props/键」；实际是「组件重写时丢了 props，配置键也随之不注册」。
→ 证据：`changelog.md` 无记录、无 ADR。

**判定**：8 个配置键缺失（P1，与维度 2/7 同源）。

## 维度 12 · 知识库

**结论**：从「单表 + 标签」升级为「库 → 文件 → 分块」三级，且接入 Coze。

**证据**：

| 项 | 原版 | 新版 |
|---|---|---|
| 模型 | `Knowledge`（title/content/tags/source/priority） | `Knowledge` + `KnowledgeBase` + `KnowledgeFile` |
| 外部对接 | `source: local/notion/feishu/web`（字段级） | `KnowledgeBase.cozeDatasetId` + `kb-sync.ts` 实际推送 |
| 文件管理 | 无 | `knowledge-files` CRUD + `trash` 软删 + `chunks` 查看 + `reparse` |
| 上传格式限制 | 无 | ADR-025：仅 docx/doc/md/txt |

**反向检验**：`Knowledge` 表是否成了死表（新旧两套并存）？
→ `grep -rn "prisma.knowledge\." src/` 需核实。若仍有引用则是双轨（技术债）。

**判定**：知识库 ✅ 大幅升级；`Knowledge` 表去留需核实（见 06 §U1）。
