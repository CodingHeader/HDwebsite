## 裁决 1 · B1：`userPrompt` 如何承接 → **选 B（存 metadata），并降级为 P2**

### 决定性证据（改变了整个前提）

我原先假设原版 `userPrompt` 是「被使用的对话模板」。**实测推翻了这个假设**：

```bash
# 原版全仓 userPrompt 分布（9 处）
src/app/api/ai-config/route.ts:34,62        ← 仅 CRUD 读写
src/app/api/ai-config/[id]/route.ts:24,48   ← 仅 CRUD 读写
src/app/manager/ai-config/page.tsx:26,43,135,381,382  ← 仅表单编辑

# 关键否定证据
grep -c "userPrompt" src/app/api/chat/completion/route.ts   → 0
grep -rn "userPrompt" src/ | grep -v ai-config | grep -v schema  → 空
```

**原版 chat 调用链的 messages 构造**（`chat/completion/route.ts:93-101`）：
```js
const systemParts: string[] = [];
if (config.systemPrompt) systemParts.push(config.systemPrompt);
if (scene?.systemPrompt) systemParts.push(scene.systemPrompt);
if (knowledgeContext) { systemParts.push(...); }
// 仅 role: "system" + 用户 messages，从未使用 userPrompt
```

### 结论

**`userPrompt` 在原版是「可编辑、可保存、但从未被消费」的死字段。**

它能存进 DB，但**不影响任何 AI 回复**。所以：

| 项 | 判断 |
|---|---|
| 是否属「能力丢失」 | **否** —— 它从未产生功能 |
| 是否需要 CCR 改 schema | **否** —— 为一个死字段动 schema 是浪费额度 |
| 正确处置 | **不恢复**，登记为「原版死字段，新版未承接属清理」 |

### 裁决

**不承接 `userPrompt`。**

从 P1-5（能力丢失）**降级并剔除**，改为「已核实为死字段，不计入退化」。

**依据三层**：
1. 原版 chat 链路 `grep` 0 命中（`chat/completion/route.ts`）
2. 全仓非 CRUD 文件 0 命中
3. messages 构造只拼 `systemPrompt`，无 user role 注入

### 若未来确实需要「用户提示词模板」

那是一个**新需求**，不是「恢复旧能力」。应作为新 ADR 立项，走独立 CCR，不在本次范围。

## 裁决 2 · B2：8 个已删键的生产旧值 → **全部恢复，但用「安全默认」策略**

### 决定性证据

我先前的顾虑是「生产库可能有非默认值，恢复后会改变视觉」。**已用原版真实数据库核实**：

```bash
# 原版 dev.db（745 KB，真实业务数据）
node -e "SELECT key,value FROM Setting WHERE key IN (...)"

输出：
bannerExtraBtnLink         "/courses"
bannerExtraBtnText         "了解更多"
bannerShowExtraBtn         "false"
fourCardsBgColor           "#f9fafb"
fourCardsBgImage           ""
fourCardsContainerAlign    "center"
fourCardsShowSection       "true"
showImageOverlays          "true"
statsBgImage               ""
topbarBgImage              "/uploads/202605/1778048088558-ne0f5b.png"   ← ⚠️ 非空
wechatQrCode               ""
```

### 关键风险点：`topbarBgImage`

值是 `/uploads/202605/1778048088558-ne0f5b.png`。

**但该文件不存在**：
```bash
test -f public/uploads/202605/1778048088558-ne0f5b.png → 不存在
ls public/uploads/202605/ → 只有 1778033453871-fihimr.png 等，无此文件
```

**结论：这个值指向的是已失效的图片引用。**

若恢复 `topbarBgImage` 并照直使用，前台顶栏会尝试加载 404 图片 → 取决于 CSS 兜底，可能显示破图或空白背景。

### 裁决

**8 个键全部恢复，但采用「安全默认」策略**：

| 键 | 原版值 | 恢复策略 |
|---|---|---|
| `showImageOverlays` | `"true"` | 原值恢复（= 新版当前行为，零风险） |
| `fourCardsShowSection` | `"true"` | 原值恢复（零风险） |
| `fourCardsContainerAlign` | `"center"` | 原值恢复（零风险） |
| `fourCardsBgColor` | `"#f9fafb"` | 原值恢复（零风险，但需确认新版是否已硬编码此色） |
| `fourCardsBgImage` | `""` | 默认空（零风险） |
| `statsBgImage` | `""` | 默认空（零风险） |
| `wechatQrCode` | `""` | 默认空（零风险，占位态） |
| `bannerShowExtraBtn` | `"false"` | 原值恢复（零风险，按钮不显示） |
| `bannerExtraBtnText` | `"了解更多"` | 原值恢复（因 show=false，不显示） |
| `bannerExtraBtnLink` | `"/courses"` | 原值恢复（同上） |
| **`topbarBgImage`** | **`"/uploads/202605/...png"`（失效）** | **默认空** ← 唯一例外 |

**唯一例外说明**：`topbarBgImage` 的原值指向不存在的文件。恢复该**值**没有意义（图已丢），且会引入破图风险。

**处置**：
1. 注册键，**默认值设为 `""`**（不是原版那个失效路径）
2. 在 ADR 中记录：原版该键指向已丢失文件，故不迁移该值
3. 若运营需要顶栏背景图，通过管理端重新上传

### 为什么这个裁决是安全的

| 检查 | 结论 |
|---|---|
| 是否改变前台视觉 | **否** —— 7 个键原值即默认值/空值；`topbarBgImage` 置空等于「无背景图」，与原版图已丢失后的实际渲染一致 |
| 是否丢失用户配置 | **否** —— 除 `topbarBgImage`（已失效）外全部保留 |
| 是否可逆 | **是** —— 仅注册键，删掉即回退 |

### 与「全部恢复原值」方案对比

| 方案 | 优点 | 缺点 | 采用 |
|---|---|---|---|
| 全恢复原值（含失效路径） | 忠实原数据 | 引入破图；等于把原版的坏引用搬过来 | ❌ |
| 全置空 | 绝对安全 | 丢失 `#f9fafb` 等有效配置 | ❌ |
| **原值恢复 + 失效值置空** | 保留有效配置，剔除坏引用 | 需逐项判断 | ✅ |

## 六、补充核实结果（已执行，支撑上述裁决）

### C1 · `HomeCard.backgroundImage` 原版数据 → **确认全空**

```bash
node -e "SELECT id,title,backgroundImage FROM HomeCard"
HomeCard 记录数: 4
  1 自学考试      null
  2 成人高考      null
  3 开放大学      null
  4 职业证书      null
```

**4 条记录全部为 `null`。**

**支撑裁决 3**：`HomeCard.backgroundImage` 在原版从未被使用。为一个数据全空的字段消耗 CCR 改 schema，投入产出比不成立。**延后裁决成立。**

### C2 · `fourCardsBgColor` → **视觉已等价，键默认值应设为 `""`**

```bash
# 原版：inline style
<section className="py-6" style={{ backgroundColor: bgColor }}>   // bgColor 默认 "#f9fafb"

# 新版：Tailwind 类名
<section className="bg-gray-50 py-6">                              // gray-50 = #f9fafb
```

**Tailwind `gray-50` 的标准值就是 `#f9fafb`** —— 两者视觉完全等价。

**这改变了 AT1.1 的一个细节**：

| 原计划 | 修正后 |
|---|---|
| `fourCardsBgColor` 默认 `"#f9fafb"`（照抄原版 DB） | **默认 `""`**，仅在用户显式设置时才覆盖 `bg-gray-50` |

**理由**：若默认写 `#f9fafb` 并走 inline style，会与新版现有的 `bg-gray-50` 类名**重复设置同一颜色**——虽然视觉无差异，但会产生「两处控制同一属性」的维护陷阱（未来改主题色时需改两处）。

**正确做法**：默认空 → 不设 inline style → 沿用 `bg-gray-50`；用户填值时才覆盖。

**同理适用于**：
- `fourCardsBgImage`：默认空（原版也是空）
- `statsBgImage`：默认空（原版也是空）

### C1/C2 对裁决的影响

| 项 | 影响 |
|---|---|
| C1 | 强化「HomeCard 延后」裁决，无需修正 |
| C2 | **修正 AT1.1 的 `fourCardsBgColor` 默认值** `"#f9fafb"` → `""` |
