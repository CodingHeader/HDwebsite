# 02 · 能力退化清单与定级

> 定级标准（不看"感觉"，看可证影响）：
> - **P0**：现有用户可感知的功能不可用（点了没反应/报错/数据丢）
> - **P1**：能力存在但失去配置/定制入口（默认行为正确，但改不了）
> - **P2**：无用户影响，仅维护成本或理论风险

---

## 一、P0 · 无

**结论：没有 P0。**

依据：9 个区块组件的 `showOverlay` 丢失后，行为等价于「恒为 true」（默认值）—— 即**原版默认状态就是现在的样子**。用户不主动关闭时，视觉零差异。

**反向检验**：会不会有用户已经在原版关闭了某个 overlay，升级后突然又显示？
→ 这是**数据迁移问题**，不是渲染问题。需核实 `Setting` 表是否存有这些键的旧值。若存有且为 `"false"`，升级后该值变成孤儿键，配置失效 → 那才是 P0。

→ **待核实项（06 §U2）**：生产库中是否存在 `showImageOverlays=false` 等 8 个已删键的非默认值记录。本机只有 `e2e.db`（测试数据），无法判定生产实际。**故 P0 暂记「无」，但附条件**。

### P1-3 · 微信二维码从配置驱动退化到硬编码

**原版**（`FloatingContact.tsx:64`）：
```jsx
{wechatQrCode ? (<img src={wechatQrCode} />) : (...)}
```

**新版**（`FloatingContact.tsx:83`）：
```jsx
<span className="text-xs text-gray-400">微信二维码</span>
```
固定展示灰框占位，**永远不可能显示真实二维码**。

**定级理由**：不是"暂时没图"，而是"没有配置入口"。即使提供图片也无处填。

### P1-4 · `/manager/ai-config` 页面断链

| 层 | 原版 | 新版 |
|---|---|---|
| 页面 | `src/app/manager/ai-config/page.tsx`（存在） | **不存在** |
| API | `/api/ai-config`（存在） | **307 重定向到 `/api/llm/providers`**（`api/ai-config/route.ts:1-30`） |
| 重定向 | — | `next.config.ts` 无、`middleware.ts` 无 |

**后果**：原版书签/文档链接 `/manager/ai-config` → 404。API 层做了兼容，页面层没做，**不对称**。

### P1-5 · `AIConfig.userPrompt` 字段丢失

**证据**：
```bash
原版: src/app/api/ai-config/route.ts:34,62   userPrompt
      src/app/manager/ai-config/page.tsx:26  userPrompt: string | null
新版: grep -rn "userPrompt" src/   → 0 命中
```

**性质**：AI 对话的「用户提示词模板」能力整体消失。`ChatScene` 只有 `systemPrompt`（系统提示）与 `greeting`（开场白），无 user prompt 模板位置。

**定级理由**：原版有 UI + API + 存储，新版三处全无 → 若原版运营曾用该模板，升级后配置无载体。

### P1-6 · `HomeCard.backgroundImage` 字段丢失

```bash
原版 schema: backgroundImage String? // 卡片背景图片URL
新版 schema: 无此字段（id/title/subtitle/icon/href/gradient/hoverGradient/shadow/sort/status）
新版 FourCards 组件: grep backgroundImage → 0 命中
```

**链路完整性**：模型无字段 → 管理端无表单项 → 组件无 prop → 前台无渲染。**四层全断**。

### P1-7 · `localImageExists` 重复实现

```bash
src/app/(web)/gallery/page.tsx:19   async function localImageExists(url: string) {
src/components/web/data/home.ts:17  async function localImageExists(url: string) {
原版 src/lib/showcase.ts:84         export async function localImageExists(...)
```

**定级理由**：两处实现各自维护，未来改逻辑（如加 CDN 判定）易漏改一处 → 行为不一致。

**核实结果**：

## 六、修复的因果顺序（关键）

P1-1 与 P1-2 同源，**必须一起做，且有严格顺序**：

```text
❌ 错误顺序：先补组件 props → 无配置键可传 → props 恒为 undefined → 死代码
✅ 正确顺序：
   1. 先在 settings-registry 注册键（有默认值，不影响现渲染）
   2. 再给组件加 props（读键 → 传组件）
   3. 再改 page.tsx 传参
   4. 最后跑视觉回归确认默认态不变
```

**理由**：键有默认值（等价原版默认 `true`），先加键**零风险**；组件加 props 时无键可传会退化成硬编码。

## 七、无法在本机验证的部分

| 项 | 原因 | 影响 |
|---|---|---|
| 生产库是否有 8 个已删键的非默认值 | 本机仅 `e2e.db`（测试数据） | 决定 P0 是否存在 |

**这些不改变「能力确实丢了」的事实，只影响「丢了多痛」的判断。**
