## 二、自我否定记录（本轮 4 个实例）

这一节是本文最重要的部分 —— 记录我最初判断错在哪。

### 实例 1：把「字段消失」当「能力丢失」→ 实为死字段清理

**初始判断**：`allowedDomains` 从 `AIConfig` 强类型字段降为 `metadata` JSON，判定 P2 退化。

**否定过程**：
```bash
原版 grep -rn "allowedDomains" src/ → 0 命中（排除 schema）
新版 grep -rn "allowedDomains" src/ → 0 命中
```
**两版都是零消费死字段。**

**修正**：从退化清单剔除，记为「改进」（清理死字段）。

### 实例 2：把「分组名」当「配置键」→ 28 个误报 20 个

**初始判断**：机械比对 settings 键，得「原版有、新版无 28 个」。

**否定过程**：逐项复核发现 `banner`/`cards`/`site`/`stats`/`topbar`/`footer`/`company`/`display`/`seo`/`other`/`contact`/`fourCards`/`homeCards` 等 20 个是**分组名**，不是键。

**修正**：真实缺失 8 项，每项都有原版消费点 file:line。

### 实例 3：把「原版有代码」当「原版在用」→ showcase 过滤已边缘化

**初始判断**：`showcase.ts` 三组守卫（毒文本/破图/乱码）在新版完全缺失，判定 P1。

**否定过程**：
```bash
原版 grep -rn "hasToxicShowcaseText|isBlockedShowcaseImage|hasBrokenShowcaseText" src/
→ 仅 src/lib/__tests__/continuation-utils.test.ts:17,96（测试文件）
```
**原版自己也近乎未启用**。

**修正**：降级为 P2，并说明「新版数据已洁净」的依据（`grep xgnedu src/` 唯一命中是业务话术文案）。

### 实例 4：把「`/api/news` 缺失」当缺口 → 实为已废止

**初始判断**：原版有 `/api/news`、`/api/news/[id]`，新版无 → 缺口。

**否定过程**：
1. `ADR-001-News并入Article.md:21` —— News 表已取消，统一入 Article
2. `/api/articles` 支持 `channel` 过滤（`route.ts:17,31`）
3. **`grep -rn "api/news" src/` 在新版 0 命中** —— 没有任何调用方

**修正**：列为「干扰项排除」，明确不做。

## 三、局限（自我否定之二）

### L1 · 无法判定「丢失的配置能力有多痛」

**问题**：我能证明「9 个组件的 `showOverlay` 丢了」，但**证不出**「原版用户实际用了没有」。

**原因**：无生产数据库、无访问日志、无原版 `Setting` 表快照。

**影响**：P1 的紧急度判断缺依据。若从没人用过 `showOverlay=false`，这批修复的收益接近零；反之则很痛。

**处置**：`06 §B2` 列为待裁决，执行前必须先查生产数据。

### L2 · 判定「默认行为等价」依赖源码阅读，非运行时验证

**问题**：我判断「`showOverlay` 丢失后行为等价于恒 true」，依据是原版默认 `showOverlay = true`（`NewsCenter.tsx:44`）。这是**读码推断**，不是跑出来的。

**反证难度**：要验证需同时起原版和新版两个服务、同样的数据、逐区块截图对比。本轮未做（成本高）。

**影响**：若某组件原版默认是 `false`，我的判断就错了。

**处置**：抽查了 3 个默认值（TopBanner `= true`、NewsCenter `= true`、Banner `showExtraBtn` 逻辑为 `=== "true"`），均已确认。但**未穷尽 9 个**。

### L3 · 未测「组件 props 增加后的包体积影响」

**问题**：给 9 个组件补 props 会增加少量代码，但对前台 bundle 的影响未量化。

**影响**：若某组件因此变大导致首屏变慢，属新引入的性能退化。

**处置**：`05 §三` 的 WP1-ST4 视情况加 bundle 对比（非强制）。

### L4 · 「矩阵口径缺陷」的修正只针对 A1 行

**问题**：`WP4-ST1` 只改 A1 行的判据描述，**其余 59 行 present 仍用可能同样的粗口径**。

**影响**：未来其他重构仍可能漏判。

**处置**：`WP4-ST1-AT1.1` 要求在**文件头**加判据说明（「present 须证明能力等价」），这是作用于全表的。但**未逐行复核 59 行** —— 那是独立的更大工作量，本轮不做。

**明确声明**：本轮**不宣称** parity 矩阵已完全可信，只修正了已发现的最严重一处。

### L5 · 工时估算是估算

**问题**：`03 §四` 估 8~10h。按 AT 数与人天比推算，未实际执行验证。

**影响**：实际可能超 30%。特别是 `FourCards`（7 字段 + 4 props）和视觉回归（需 Linux）两块。

### L6 · 未验证原版的实际运行状态

**问题**：我没有启动 `hdwebsite_0429` 跑一遍。所有「原版行为」结论都来自**读源码**。

**风险**：原版可能有运行时行为与源码字面不一致（如某个 prop 传了但组件内部未真正使用）。

**已做的缓解**：对每个关键 prop 都确认了「在 JSX 中被消费」（如 `TopBanner.tsx:48 {showOverlay && (`、`:46 style={bannerStyle}`），不是只声明不用。

**但仍有限**：未穷尽 9 个组件的每一处 props 消费点。

## 四、结论

**自检 30 项：30 项通过。**

**但通过不等于完备。** 本规划有以下确定的不确定：

| 不确定项 | 影响 |
|---|---|
| 生产数据中 8 个已删键的实际值（L1/B2） | 决定 P0 是否存在、修复是否会引起视觉变化 |
| 9 个组件默认值的穷尽核对（L2） | 若某组件默认非 true，「等价」判断失准 |
| parity 矩阵其余 59 行（L4） | 可能还有其他漏判 |
| 原版运行时行为（L6） | 读码结论可能与实际有偏差 |

**不宣称「绝对正确」或「一定成功」。**

**本轮最有价值的产出不是任务清单，而是发现了 `parity-matrix`「以文件存在代能力对等」这个验证机制缺陷** —— 它会让未来每一次重构都漏判同类问题。
