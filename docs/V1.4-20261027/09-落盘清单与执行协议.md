## 二、每卡取卡循环（严格按序）

```
1. 拉代码   git fetch origin upgrade && git pull --ff-only
           核对 git rev-list --left-right --count origin/upgrade...HEAD == 0 0
2. 读状态   cat docs/V1.4-20261027/state.json
           取 status=ready 且 depends_on 全部 done 的卡
3. 领卡     改 status 为 in_progress
4. 读卡     docs/V1.4-20261027/tasks/<卡号>.md
5. 构建前置 ★ 若要跑 e2e：先 npm run build，并确认 BUILD_ID 新于 src
             （tests/e2e/global-setup.ts 已硬校验，stale 会直接抛错）
6. 执行     只在「允许修改」路径内写入，越界即 FAIL
7. 门禁     串行：lint && typecheck && test && build + 卡内验证命令
8. 证据     docs/design/06_validation/evidence/V14/<卡号>/execution.md
            必含：5W1H、改动文件、验收逐条结果、命令输出摘要、BUILD_ID、UNKNOWN
9. 提交     git commit -m "feat(V14-XXX): ..."（小而聚焦）
10. 推送    git push origin upgrade；被拒只 rebase，禁 force
11. 心跳    state.json 改 done + commits + note；EXEC-log 追加一行
12. 回到 1
```

## 三、四条铁律（均有实测教训）

1. **禁止并行跑 `npm run build` 与 `npm test`**
   实测并行产 `Hook timed out in 10000ms`（2 文件）；单跑/串行全绿。假红会把后续轮次引向错误方向。

2. **e2e 证据必须附 `BUILD_ID` 时间戳**
   实测 `BUILD_ID` 17:54 < `src` 18:13 → e2e 报 `apply-chat` 失败；rebuild 后同一源码 79/79。守卫已加。

3. **visual 只认 Linux CI，且需连续 ≥2 次绿**
   Windows 字体差异不可分离；单次绿不足以证明（4 次 run 曾失败 1 次）。

4. **不得改测试迁就实现**
   若测试失败，先判"实现错 / 测试错 / 环境错"，**不得**直接放宽断言或改 mock 绕过。V13 曾有 5 个用例因此差点被掩盖（实际是实现缺陷）。

## 五、判定与熔断

| 情形 | 处置 |
|---|---|
| 完成判定 | `AGENTS.md §6`：diff 符合 ∧ 验收逐条有结果 ∧ 可复现 ∧ 守卫通过 ∧ 未改冻结面 |
| 独立验证 | 由**另一会话**只看 diff + 运行结果，出 `verify.md`（PASS/FAIL/UNKNOWN） |
| 同卡连续 2 次 FAIL | 熔断：停改代码 → 重写卡/升档/标 blocked |
| 遇外部条件 | state 标 blocked + 原因，转下一张，**不停工** |
| 需改冻结面 | 停该子项，写 `ccr/V14-CCR-<n>.md`（本轮预期不会发生） |
| 剩余卡全部 blocked | 才允许停下，并输出 zip 规划包 |

## 六、推送失败降级

若 `git push` 因凭据/网络失败：

1. `zip -r backups/release/HDwebsite-V1.4-20261027.zip docs/V1.4-20261027`
2. state 相关卡标 `blocked`（reason = 推送不可用）
3. 最终回复给出包路径与恢复步骤，**不虚报双端一致**
