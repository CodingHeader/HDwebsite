# 01 · 需求基线复核与深度分析（V0.7）

## 1. 复述与拆解

弘道教育官网（前台）+ 管理后台（/manager）+ 微信公众号的统一运营平台：自动采集学校/部门政策新闻 → 进入知识库与内容中枢 → 审核后自动发布到官网与公众号 → 官网与公众号共用 AI 客服（多模型优先级/默认/兜底、知识库检索）→ 发布前、模型余额低、系统错误时邮件提醒多名收件人。
- **用户**：访客（前台、公众号粉丝）。**管理端**：超管、编辑、运营等角色（RBAC，permissionCatalog）。**系统边界**：单机 Next.js + SQLite + 进程内任务（REQ-C-003：禁止 Redis/MQ/无头浏览器/独立 worker）；外部仅 Coze、微信、SMTP、LLM 供应商。
- 关键词：功能对等 main、前台像素冻结、管理端顶级体验、Coze 知识库（仅 Word/MD/TXT）、mock 优先、单主线 upgrade。

## 5. 隐含要求与前置条件

1. 每张卡开工前 `git pull --ff-only origin upgrade`，完工后小提交并推送（单主线不再有 lane 隔离，冲突只能靠所有权不相交 + 频繁同步）。
2. 越权修复必须同时覆盖"间接提权"：改自己角色的权限、给自己换角色、改他人密码后登录。
3. 测试必须在无 `.env`、无 `prisma/dev.db` 的干净检出上可复现（CI 前提）。
4. 推送凭据：remote URL 不得含 token；临时凭据文件 600 权限，用完删除（用户安全规则）。
5. 独立验收者不得是原执行者（commit 作者/提示词归属核对）。

## 6. 深度分析（5W1H → 追问 → 钢人 → 判断）

### What
已完成约 33 张卡的实现，但"完成"多数是执行者自报；剩余 27 张承接卡（B 6、D 13、W2 8）+ 11 张新卡。最大的真实缺陷不是功能缺口，而是**权限模型可被绕过**与**验收链缺环**。

### Why
越权缺陷长期无人负责的根因：V0.4~V0.6 把它登记在"风险"而非"任务"，且 users/roles 路由归 B-02（withApi 迁移，纯包装），B-02 的验收标准是"信封不变"，天然不会修语义。只改 B-02 范围会把缺陷原样包进 withApi。

### Where / When
`src/app/api/users/**`、`src/app/api/roles/**`、新增 `src/lib/authz/**`。必须先于 B-02（同文件），且先于 W2-05 全量回归与 W2-07 推送打包。

### Who
Hark（opus）写修复；P2 按本文件 §3 清单独立写黑盒用例（不读实现）；独立验证者只看 diff + 结果。

### How
先红后绿：攻击用例先失败 → 实现 `assertNoEscalation` → 用例转绿 → P2 黑盒复核 → 合入。

### What if
- 若超管角色不是 slug `super-admin` 而是 isSuper 字段多角色：修复以 `isSuper` 判定，不以 slug。
- 若前端依赖"非超管可改角色权限"的旧行为：E-xx 页面会出现 403 → V7-V-E 验收时回归 e2e 暴露，UI 以 forbidden 态展示（契约 uxStateSchema 已含 forbidden）。
- 若 B-02 先被人做了：B-02 必须在 V7-SEC-02 之上 rebase，不得覆盖校验代码（卡内依赖 + 所有权串行）。
- 若测试通过但运行时失败：W2-05 Linux e2e 覆盖 auth.spec 与 users 管理页。

### 苏格拉底追问（摘要）
- 凭什么说 E1 可利用？`roles/[id]/route.ts` PUT 只要求 `role:edit`，update 的 data 直接写 `input.isSuper`，唯一拦截是 slug=super-admin；对自己所属的非内置角色无任何拦截。证据来自 4cbd9c1 当前文件。反证：中间件是否另有拦截？`requireAuth(request,"role:edit")` 只做权限点校验（auth-permission.test.ts 覆盖的也是这一点），未发现其他拦截 → 结论成立，但未做运行时复现（标"代码证据确认，运行时待 SEC-03 复现"）。
- 597/599 是否意味业务回归？kb-api 用例在 30s 下通过（只是慢）；kb-coze 是测试读开发库所致 → 不是业务回归，是测试隔离缺陷。

### 钢人论证
- 支持"先做 S0"：账号接管级风险；同文件串行使其必须早于 B-02；工作量半天到一天。
- 反对："先补独立验收，可能发现更严重问题"。回应：S2 验收与 S0 无共享文件，DAG 中二者同处 L0/L1 并行，不互相阻塞。
- 反对"V0.7 不该再加新卡"：新卡 11 张均有代码证据（F3~F6、F11、X1），无凑数卡。

### 最终判断
- 结论：进入 V0.7 执行；第一刀 = S0 安全热修（Hark）∥ S1 测试卫生（P2）∥ D 线 L0（P3）∥ S2 验收（P1/P2）。
- 局限：e2e/visual 未在本轮运行；越权仅代码级确认；真实外部联调全 UNKNOWN。
- 是否允许进入下一阶段：**允许**（V7-Q1 需用户回答以确定 SEC 执行者）。
