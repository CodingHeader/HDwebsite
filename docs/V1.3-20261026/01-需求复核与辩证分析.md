## 2.2 第一轮：5W1H 发散

### What（客观事实）

1. **任务要求**：检查"未被实现的需求"，建立统一规划体系，按步骤一个 md 一个步骤，推到 GitHub 或打包。
2. **已实现（有证据）**：126 个 API 路由、42 个管理页、16 个前台页、48 个模型、8 个迁移、85 个设置键；单测 1853、e2e 79、a11y 12 全绿；`parity-matrix.md` 对等主表 57 行 = 50 present + 7 replaced、missing 0 / partial 0。
3. **未实现/未证明（本轮查出）**：
   - **质量守卫层的缺失**：a11y 未接入 CI（孤儿测试）、visual CI 红且不可判、e2e 在 Windows 上可测旧构建（已修）。
   - **实现缺陷**：限频双源并存（硬编码 10 按 IP + 设置 20 按 scene:identifier）。
   - **文档欠账**：16 个需求文档共 **102 条 `- [ ]`** 未勾选，其中含已实现项，导致"剩余什么没做"无法从文档回答。

4. **已被真实证据证明的**：F1~F9 全部门禁结果（本次运行，附命令）。

### Why（深层原因）

1. **为什么需要本轮**：V1.1 交付功能、V1.2 收敛 E2E，但"功能已写"与"需求已被证明"之间存在系统性缺口。台账写 `done` 的卡，其验收条目在需求文档里仍是 `- [ ]`。
2. **直接原因**：验收条目散落在 `REQ-F-*` 的 checkbox 中，而执行证据写在 `evidence/**`，两者**没有强制回写机制** → 台账与需求文档双轨漂移。
3. **根本原因**：门禁分两类但只守了一类——**代码门禁**（lint/tsc/test/build/e2e）进了 CI；**需求门禁**（a11y、visual、性能、限频一致性）没有进入 CI 或没有单源。缺少一个"需求 → 验收命令 → CI 步骤"的可追溯映射。
4. **只改表面的后果**：如果本轮只补 12 张卡而不建立"需求条目 ↔ 验收命令"映射，下一轮仍会出现同样的漂移。
5. **风险**：修复限频会改变真实用户可发消息次数；修 a11y CI 接入可能暴露首页既有违规（前台冻结，不能改样式）。

## 2.3 第二轮：苏格拉底追问（对关键结论逐条拷问）

### 结论 A：`apply-chat` 失败是"旧构建"而非代码缺陷

1. 凭什么？`BUILD_ID` 17:54 < `chat-session.ts` 18:13，且 build 后同一源码单跑 PASS。
2. 证据来自哪？文件 mtime + `npm run build` + 单测/单跑 e2e 结果。
3. 是最新真实代码？是，`cbaaf55`。
4. 有相反证据吗？trace 显示 4 次并发 GET + 400，**看起来**像修复失效——这是最强的反证。
5. 会不会把表象当根因？**会**，见第 4 点。我最初的判断就是"修复没生效"。
6. 遗漏了异常路径？已补：用"重建后再跑"区分"代码没修好"与"测的是旧代码"。
7. 前提是什么？构建产物必须与源码同步（`BUILD_ID` 晚于所有 src mtime）。
8. 前提不成立时结论还成立吗？**不成立**——这正是原守卫的漏洞所在。
9. 需额外验证吗？已做：79/79 全量复跑。
10. 足以支持"PASS"吗？**足以**，且附带新纪律：e2e 证据必须记 `BUILD_ID` 时间戳。

### 结论 B：限频是"双源实现缺陷"而不只是"两种口径"

1. 凭什么？两处独立阈值（10 / 20）、两种粒度（IP / scene:identifier）、一处不可配。
2. 证据？`stream/route.ts:22`、`guard.ts:27`、`settings-registry.ts:162` 行号可核。
3. 最新代码？是。
4. 反证？可能有人主张"这是有意的双层防护"。**反对有效但不足以推翻**：双层防护应"同阈值同口径"，否则后台配置失真。
5. 表象 vs 根因？根因是**缺少单一限流源（single source of truth）**。
6. 遗漏？公众号 `chatOnce` 走 guard 单源，官网 SSE 走双源 → 两端行为不一致，已确认。
7. 前提？`AIChatHistory` 有 `ipAddress` 且被写入。
8. 前提破了？若 IP 为空，A 通道恒不触发 → 实际只有 20 生效，行为更不可预测。
9. 需验证？`V13-RL-01` 用契约测试钉住"单一源"。
10. 足以判定缺陷？**是**（`存在缺陷`）。

### 结论 C：visual 红灯不可归因

1. 凭什么？className 变更 0 行 + 33 个提交 + artifact 不可下载。
2. 反证？`ChatWidget` 有 +29/−8 变更，若其影响布局则会真回归。**反证部分成立** → 不能排除，只能标 UNKNOWN。
3. 足以判 PASS 吗？**绝不**。标 `证据不足`。

## 2.4 第三轮：双向钢人论证

### 命题：「V1.1/V1.2 已把 main 的功能全部实现，剩下的只是修门禁」

**支持**：`parity-matrix` 57 行 missing 0 / partial 0；126 路由 / 42 管理页 / 16 前台页实测存在；e2e 79 覆盖登录、CRUD、缓存失效、JSON-LD、首页区块、知识库、通知、响应式、五态；单测 1853。

**反对（更强的三点）**：
1. **"存在"≠"可用"**：`parity-matrix` 的 present 判定依据多为"文件存在 + 行数 ≥ main"，这不能证明交互闭环。反例：本轮就发现限频配置在 UI 可见但**对官网通道无效**。
2. **验收条目 102 条未勾选**：包含"刷新后会话可续传""公众号 5s 被动回复""余额阈值告警"等**可自动验证**的项，却没有任何映射到测试的证据。
3. **守卫缺位**：a11y 不在 CI、前台 a11y 覆盖 0、visual 不可判 → 质量结论缺乏独立守卫。

**裁决**：支持论证在"代码量/路由数"层面成立；反对论证在"需求已被证明"层面成立且更关键。→ **本轮应做"需求反勾 + 守卫补位"，而不是再堆功能。**

### 命题：「限频应等用户裁决后再动手」

**支持**：MUST 冲突（REQ-F-009 §38 vs ADR-034），代理规则明令不替用户裁决。

**反对**：双源本身是缺陷，与阈值取值正交；若等裁决，则"后台配置无效"这一确定性缺陷继续存在，且裁决后仍要再做一次重构。

**裁决**：拆开——`V13-RL-01` 只做"单一源 + 设置驱动 + 契约测试"，**阈值默认取当前生效的更严值 10**（保证不回退、不放松风控）；`V13-Q2-01` 保留待裁决，裁决后仅改一个常量与一处断言。**这样既不替用户裁决，也不让缺陷挂账。**

## 2.5 第四轮：重构与最终判断

### 明确结论

1. **代码实现层面**：main 对等功能**基本齐备**（`已确认`，证据 = parity 矩阵 + 126 路由实测 + e2e 79 绿）。
2. **需求证明层面**：**存在系统性缺口**（`已确认`）——102 条验收未勾选、a11y/visual/性能三类守卫缺位或不可判。
3. **实现缺陷**：限频双源（`存在缺陷`）、e2e 新鲜度守卫在 win32 失效（`存在缺陷`，**已修并验证**）、seed-visual `--check` 口径（`存在缺陷`，低危）。
4. **不可判定**：visual 红灯归因、真实第三方联调（`证据不足` / `UNKNOWN`）。

### 成立前提

- 构建产物与源码同步（否则所有 e2e 结论失效）。
- 门禁串行执行（否则出现假红，见 `00-事实基线.md` §4）。
- Linux CI 为 visual 唯一判定环境。

### 局限

- 未取得 CI artifact（401/403），visual 无法逐组 diff。
- 未做真实微信/SMTP/Coze 联调（无凭证）。
- 本轮仅抽样若干行号，未逐行审计 126 路由。

### 风险

- 限频收口若取值不当会放松风控 → 默认取 10（更严）规避。
- 接入 a11y 到 CI 可能暴露既有违规 → 管理端阻断、前台登记不阻断。
- 需求反勾若草率勾选会造成"假闭环" → 要求每条附证据路径，无证据只能标 UNKNOWN。
