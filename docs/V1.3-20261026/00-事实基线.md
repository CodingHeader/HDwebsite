## 3. 五项穿刺结论（本轮的核心发现）

### 3.1 测试基础设施会"测到旧构建"——已实证，已修

- **现象**：`npm run test:e2e` 首次运行 **1 failed**（`apply-chat`），断言 `MOCK_REPLY` 30s 超时。
- **排除项**：解包 trace（`.cache/e2e/test-results/.../trace.zip`）确认失败形态仍是 **4 次并发 `GET /api/chat/session` → 200，随后 `POST /api/chat/stream` → 400**，与 V1.2 记录的根因一致 → 说明代码仍是修复前的行为。
- **真因**：`.next/BUILD_ID` mtime = **17:54:31**，`src/app/api/chat/session/route.ts` + `src/lib/chat-session.ts` mtime = **18:13:36** → **构建陈旧**。`npm run build`（19:00）后同一份源码 apply-chat **单跑 PASS**、全量 **79/79 PASS**。
- **为什么守卫没拦住**：`tests/e2e/global-setup.ts:70` 的 `if (!useStandalone) return null;` **早于** `:73` 的新鲜度校验；`useStandalone = process.platform !== "win32"`（`:27`），`next.config.ts:7` 在 win32 上 `output: undefined` → **Windows 上该守卫永远被跳过**。
- **影响面**：Windows 本机上任何"e2e 全绿"结论，若不附 `BUILD_ID` 时间戳，都不能证明测的是当前源码。
- **处置**：本卡已修（新鲜度校验前移到平台分支之前，报错含两侧时间戳），tsc/lint 通过，e2e 复跑 79/79 全绿。

### 3.2 限频双源并存——既遂缺陷

| 通道 | 位置 | 阈值 | 粒度 | 可配置 |
|---|---|---|---|---|
| A | `src/app/api/chat/stream/route.ts:22` | 硬编码 `10` | 按 **IP** 查 `AIChatHistory` 60s 计数 | **否** |
| B | `src/lib/llm/guard.ts:27` | `GUARD_DEFAULT_RATE_LIMIT = 20` | 按 `scene:identifier` 进程内滑窗 | 是（设置键 `chatGuardRateLimitPerMin`，`settings-registry.ts:162` 默认 `"20"`） |

- 实际有效阈值 = **两者先到者**（10 或 20 谁先触发谁是真实上限），且 A 通道按 IP 聚合会误伤同一 NAT 下多个真实访客。
- 后台"客服限流（次/分钟）"设置对 A 通道**完全无效** → 管理员看到的配置与实际行为不一致（可观测性缺陷）。
- `docs/design/02_requirements/features/REQ-F-009-官网公众号AI客服.md:38` 写"默认 10 次/分钟"；`ADR-034 §2.3` 采纳 20 并被 `settings-registry.test.ts` 钉住 → **MUST 冲突**，须用户裁决（`V13-Q2-01`）。
- 但**双源并存本身是实现缺陷**，与"10 还是 20"的裁决无关，可在裁决前先收口（`V13-RL-01`）。

### 3.5 seed-visual 自检失败是本地库脏，非脚本缺陷

- `prisma/fixtures/visual/counts.json` 定义 `Article: 25`；`prisma/seed-visual.ts` 按 `ID_BASE + 200 + i`（i=1..25）写入 **9201~9225**。
- 本地 `prisma/dev.db` 实有 visual id **26 条**，多出的 `9226 = ('测试文章','draft')` 是**人工测试残留**，不是种子产物（种子 25 条齐全，0 缺失）。
- **脚本 design 是幂等的**（按固定 id 先删后插），但**只删自己那 25 个 id**，删不掉外部残留 → `--check` 因总数 +1 而误报。
- 处置建议：`V13-SEEDVIS-01` 让 `--check` 只统计自己 id 区间（或给出"非种子行"清单），避免本地脏库误判为 CI 失败。

## 4. 关于"单测并发误报"的口径登记

首次 `npm test` 与 `npm run build` **并行**执行时，出现 `kb-api.test.ts` / `llm-usage.test.ts` 两个 `Hook timed out in 10000ms`（exit 1）。单独运行这两个文件 → **30/30 PASS**；后续 `npm test` 独立运行 → **90 文件 / 1853 用例全绿**。

**口径**：这是**测量方法引入的假失败**（build 抢占 CPU/文件句柄），不是代码缺陷。**登记为纪律**：门禁验证必须串行执行，禁止为省时间并行跑 build 与 test；否则会产出假红并把后续轮次引向错误方向。
