# 05 连续执行协议（V1.3）

> 单主线串行协议（沿用 V0.7 起的 `upgrade` 单主线；**不新建分支**，遵守用户明令）。

## 一、每卡循环（严格按序）

```
1. 拉代码      git fetch origin upgrade && git pull --ff-only origin upgrade
               记录 HEAD 与 git rev-list --left-right --count（必须 0 0）
2. 读状态      cat docs/V1.3-20261026/state.json
               找 status=ready 且 depends_on 全部 done 的卡
3. 领卡        把该卡 status 改 in_progress（本文件 §三 心跳格式）
4. 读卡        docs/V1.3-20261026/tasks/<卡号>.md（输出/允许修改/验收/验证命令）
5. 构建前置    ★ 若该卡要跑 e2e：先 npm run build，并核对
                 BUILD_ID mtime > src 最新 mtime（V13-E2E-FRESH-01 守卫已强制）
6. 执行        只在"允许修改"路径内写入；越界即 FAIL
7. 门禁        串行执行（禁止并行跑 build 与 test，见 §二）
               npm run lint && npm run typecheck && npm test && npm run build
               + 该卡"验证命令"节
8. 证据        docs/design/06_validation/evidence/V13/<卡号>/execution.md
               必含：5W1H 简版、改动文件、验收逐条结果、命令原始输出摘要、
                     BUILD_ID 时间戳、UNKNOWN 及原因
9. 提交        git add <仅本卡文件> && git commit -m "feat(V13-XXX): ..."
               前缀：feat/fix/test/docs/chore(V13-XXX)
10. 推送       须用户已授权（本包授权来自 2026-10-26 用户指令）
               被拒只 rebase，禁止 force
11. 心跳       改 state.json 为 done + commits + note；EXEC-log 追加一行
12. 回到 1
```

## 二、三条铁律（本轮新增，均有实测依据）

1. **禁止并行跑 `npm run build` 与 `npm test`**
   - 实测：并行时 `kb-api.test.ts` / `llm-usage.test.ts` 出现 `Hook timed out in 10000ms`（exit 1）；单跑 30/30 PASS，串行全量 1853 PASS。
   - 并行会产出**假红**，把后续轮次引向错误方向。
2. **e2e 证据必须附 `BUILD_ID` 时间戳**
   - 实测：`BUILD_ID` 17:54 < `src` 18:13 → e2e 1 failed；重建后 79/79。无时间戳的"全绿"不可信。
   - `V13-E2E-FRESH-01` 已在 `tests/e2e/global-setup.ts` 加硬校验（src 比 BUILD_ID 新即抛错）。
3. **visual 只在 Linux CI 判定**
   - Windows 字体渲染差异无法与真实样式差异分离（V0.7 实测），本机跑 visual 结果不计为证据。

## 三、心跳格式（EXEC-log）

```markdown
- 2026-10-26 19:40 | V13-RL-01 | in_progress | HEAD=cbaaf55 | 起点
- 2026-10-26 20:05 | V13-RL-01 | done        | commit=xxxxxxx | 门禁四连绿，单源生效
```

## 四、阻塞与熔断

| 情形 | 处置 |
|---|---|
| 遇外部条件（凭证/权限/网络） | state 标 `blocked` + `blocked_reason`，转下一张就绪卡，**不停工** |
| 同一张卡连续 2 次 FAIL | 熔断：停止改代码 → 重写该卡 / 升档 / 标 blocked |
| 同一方向连续 2 次独立验证 FAIL | 停止该方向，升级给用户 |
| 需要改冻结面 | 停止该子项，写 `ccr/V13-CCR-<n>.md`（见 `03-契约与迁移增量.md` §四） |
| 剩余卡全部 blocked | 才允许停下，并输出 zip 规划包 |

## 五、独立验证（防自证循环）

- 执行者 ≠ 判定者：每卡完成后，由**另一 Agent / 另一会话**只看 `git diff` + 命令输出，给 PASS/FAIL/UNKNOWN。
- 验证报告落 `docs/design/06_validation/evidence/V13/<卡号>/verify.md`，由被验证方原样提交。
- 验收标准**只认规划阶段写定的内容**（`tasks/<卡号>.md` 的"验收标准"节），不得事后追加。

## 六、推送失败的降级

若 `git push` 因凭据/网络失败：

1. `git bundle` 或 `zip` 打包 `docs/V1.3-20261026/` + 本包已改代码文件到 `backups/release/HDwebsite-V1.3-20261026.zip`；
2. state.json 相关卡标 `blocked`（reason = 推送不可用）；
3. 在最终回复中给出包路径与恢复步骤，**不虚报双端一致**。
